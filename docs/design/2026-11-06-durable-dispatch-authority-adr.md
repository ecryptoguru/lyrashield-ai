# ADR: closed durable scan-dispatch authority foundation

**Status:** implemented and closed, not admitted. This ADR records the corrective schema (`packages/db/prisma/migrations/20261105130000_durable_dispatch_authority`), the broker transaction layer (`packages/db/src/scan-dispatch-authority-broker.ts`) as well as the disposable-PostgreSQL fixture (`packages/db/scripts/tests/scan-dispatch-authority-pg.sh`). It amends the design direction in `2026-11-04-dispatch-authority-boundary.md`. Nothing here deploys or opens an epoch. It does not change a production role. It does not grant runtime consumers access to authority tables. Production admission stays held.

## Decision

Keep scan-admission authority durable, closed and broker-owned:

1. **Queue publication is transport, not authority.** BullMQ publication moves to `ScanQueueOutbox` (scan-keyed, no attempt foreign key). `QUEUE_PUBLISH` is removed from `ScanDispatchCommandType`; supervisor commands are only `PREPARE`, `START_PAID`, `START_UNMETERED`, `STOP`, `RECONCILE`.
2. **One durable operation per scan.** `ScanDispatchOperation` is created at admission. It is keyed by scan ID with a `requestDigest` of the admitted scope; it is the authoritative lookup for lost-ACK recovery. The worker-bound `ScanDispatchAttempt` is created later by the broker and only while its operation is `QUEUED`/`WAITING_CAPACITY`/`PREPARING`.
3. **Every state change is receipt-bound.** The supervisor journal is mirrored into `ScanSupervisorReceipt` (monotonic per-instance sequence, hash-chained, signed, bound to its outbox command). Physical transitions, outbox acceptance/completion and terminal release receipts all require authenticated supervisor evidence; free-text evidence references are removed.
4. **UNKNOWN is sticky.** Any lost COMMIT response, dead supervisor mid-command or journal/database disagreement leaves the operation and its physical execution in `UNKNOWN` until an accepted `RECONCILE` command resolves it. Terminal release is rejected while any command for the operation is unresolved.
5. **Capacity is not released here.** The broker mutates the reservation only `RESERVED → RUNNING` at the paid-start boundary. `ScanDispatchReleaseReceipt` records terminal evidence with a `capacityDisposition` (`RELEASED`, `SETTLED`, `REVIEW_REQUIRED`); wiring it into slot deletion or reservation reuse is future integration work that must require the receipt. The paid-start transaction's full write set is: `Scan.status='RUNNING'` (+`startedAt`/`updatedAt`); reservation `RESERVED→RUNNING`; one `ScanEvent` (`billable_boundary`, `retryPolicy=fresh_scan_required`); `ScanDispatchStart`; `ScanDispatchOutbox(START_PAID)`; and operation `→START_PENDING`; prepare writes attempt + physical hold + `PREPARE` outbox + operation state, stop writes `STOP` outbox + `STOPPING`, reconcile writes `RECONCILE` outbox only. The broker identity holds no more than the `leasePrismaUnit` grant list in the broker header comment; proving least-privilege against the real admission identity stays an admission gate.

## Topology and roles

- **Migration owner** (superuser in the fixture; the deployment identity in production): owns schema and grant changes. Not a runtime identity.
- **Broker:** the only writer of authority tables, through the typed transaction layer. It holds the connection until COMMIT, sets its own `synchronous_commit = remote_apply`; it treats a missing COMMIT acknowledgement as `COMMIT_OUTCOME_UNKNOWN`, never as failure or success.
- **Supervisor:** produces receipts behind its own signed journal; the broker mirrors verified receipts. The supervisor itself has no authority-table write path here.
- **Application/worker runtime roles** (`app_runtime_prod`, `app_system_prod`, `app_runtime_ci`, fixture `dispatch_authority_runtime`): the migration revokes all privileges on the eleven authority tables from `PUBLIC` and from these roles; `FORCE ROW LEVEL SECURITY` applies. The disposable fixture proves `SELECT/INSERT/UPDATE/DELETE` are all denied and a direct insert raises `42501`.

## Lock order

Fixed order, in effect in every broker transaction: authority epoch (`FOR SHARE`) → user advisory → workspace advisory (raw `hashtextextended(workspaceId, 0)`, the dominant product key; the prefixed `scan-admission:` variant is not taken — see broker header) → target advisory (`hashtext(targetId)`, matching the scan-creation path) → sponsor account advisory → scan row (`FOR UPDATE`) → operation row (`FOR UPDATE`) → attempt/physical/outbox rows (`FOR UPDATE`). It re-reads all protected state after the scan-row lock, rejects isolation drift; it fails closed on lock timeout. This matches the existing product ordering (user → workspace → account → scan) and extends it; no second, diverging order exists in this layer.

## State machines

- **Operation:** `QUEUED → WAITING_CAPACITY → PREPARING → PREPARED → START_PENDING → ACTIVE → STOPPING → TERMINATED`, with `REJECTED` from pre-start states and `UNKNOWN` enterable from any non-terminal state. `UNKNOWN` exits only to `TERMINATED`; terminal states require a reason. Identity fields are immutable; history cannot be deleted.
- **Queue outbox:** `PENDING → LEASED → PUBLISHED`, with `UNKNOWN → PUBLISHED` after verification only.
- **Supervisor command outbox:** `PENDING → LEASED → DELIVERED → ACCEPTED → COMPLETED|REJECTED`, with `UNKNOWN` enterable at any point; `UNKNOWN` exits to `COMPLETED|REJECTED` only after an accepted `RECONCILE`. Acceptance onward requires a matching non-UNKNOWN supervisor receipt.
- **Physical execution:** `RESERVED → PREPARING → DISPATCH_PENDING → ACTIVE → STOP_REQUESTED → CLEANUP_PENDING → STOPPED`, plus `UNKNOWN` and `NEVER_DISPATCHED` terminals. Each transition must cite exactly one supervisor receipt whose type and command match the transition. Leaving `UNKNOWN` requires a completed `RECONCILE`, and `STOPPED`/`NEVER_DISPATCHED` require every command of the operation to be resolved.
- **Capacity:** the broker only advances `RESERVED → RUNNING`; the unresolved-attempt quarantine key keeps one unresolved physical attempt per scan.

## Recovery and failover rules

- Lost COMMIT: the caller re-queries by the same `operationId`; `status()` returns the durable state or `STATUS_UNAVAILABLE`. Replay of `prepare`/`startPaid`/`stop` returns the already-committed identities for the same operation; replay with changed worker, grant or epoch identity raises `DISPATCH_REPLAY_CONFLICT`. A replay can never mint a second attempt or paid start or STOP.
- Lost ACK is symmetric for the supervisor: redelivery of a command is status, not a second execution, and the supervisor receipts table rejects non-contiguous or mis-linked journal entries.
- Failover/epoch loss: authority epoch `1` (`scan-authority-baseline`) is created closed and cannot be reopened; an old epoch cannot be revived after a restore. Attempt insertion requires an open epoch and a live worker grant covering the whole attempt window in that epoch. A database/supervisor journal disagreement fails closed to `UNKNOWN` and stays quarantined.
- Deletion and scope change: a soft-deleted scan blocks operation creation; a deleted target or any change to the admitted plan, policy, sponsor, attachments, delegation version or capacity identity invalidates the stored digest and fails `prepare` with `DISPATCH_SCOPE_CHANGED` instead of silently upgrading authority.

## Rollback

Forward-only. Rolling back must not delete attempts, receipts, epochs or holds (every authority table rejects `DELETE`); a rollback target that does not understand these tables must leave admission closed. This ADR does not authorize production application of the migration; before deployment the grant block executes only if the corresponding roles exist.

## Verification boundaries

The disposable fixture proves, on real schema and real PostgreSQL 17: migrate-deploy parity (zero Prisma drift); atomic prepare/paid-start/stop/reconcile transactions; concurrent-prepare serialization; revoked/expired-grant and closed-epoch rejection; replay conflict detection; scope-change and target-deletion invalidation; single terminal release with duplicate-release rejection; runtime-role denial; lock-contention fail-closed atomicity; and lost-COMMIT recovery through an intentionally dropped COMMIT response. It does not prove managed-service failover, real supervisor signatures or production role membership; those remain gates of the supervisor/provider task and hosted qualification.

### Internal shadow admission qualification

`createScan(params, transaction, { dispatchAuthority: "shadow" })` is an internal service seam, separate from customer request parameters. No current manual, scheduled, REST, delegated or retest caller selects it. Its shared admission transaction retains the immutable plan, initiating-user slot, sponsor-account reservation, queued event and separate delegated operation provenance, then creates a new scan-bound dispatch operation using `app.scan_dispatch_scope_digest` and a queue outbox from persisted scan fields and server-normalized optional focus. A missing digest or any write failure aborts that same transaction.

Both records commit quarantined as `UNKNOWN`; the queue row records `SHADOW_ADMISSION_CLOSED`. The required initial `QUEUED` operation insertion transitions to `UNKNOWN` before commit. Existing broker preparation and SQL queue leasing reject these states, including with a valid grant in an open epoch. The operation remains non-preparable even if the outbox receives a publication timestamp. No authority role grants, epoch opening, queue publisher, worker paid-start path or receipt consumer is activated. The existing `enqueueScan` path stays in effect.

The disposable fixture additionally checks admission rollback after an outbox failure, concurrent admission serialization, distinct delegated/dispatch identities, canonical SQL digest parity, sponsor ownership, shadow preparation/leasing denial and retained runtime-role denial. It seeds and validates its own fixture epoch without suite-order dependencies.

### Closed queue publication qualification

The additive migration `20261111120000_scan_queue_publication_receipts` retains nullable, immutable canonical queue payload bytes and positive publication receipt bytes with SHA-256 checksums. Payloads use the strict shared `ScanJobData` schema and a 4 KiB byte cap; publication receipts use a 2 KiB cap. Legacy null payloads remain unavailable and cannot be backfilled. The migration changes no grants or admission settings and opens no epoch. Its triggers run with the invoker's privileges.

`createScanQueueOutboxDispatcher` defaults to `closed`; only an explicit internal `qualification` setting runs it. There is no environment switch, production registration or customer-callable selector. The injectable trusted queue adapter must use `enqueueScan` and exact `getScanQueue().getJob(jobId)` plus job-state readback. The disposable adapter exercises those existing helpers against a key-restricted Redis identity.

The publisher locks the persisted operation, scan and outbox with workspace and sponsor account RLS, recomputes the existing SQL scope digest, verifies the immutable execution plan and reconstructs the whole admitted payload. A single bounded lease permits one publication attempt using the same scan/job identity. For rows with immutable payload bytes, SQL rejects resetting an attempted publication to `PENDING` or acquiring a second lease. PostgreSQL's clock determines lease validity. Publication requires the exact queue, job name, job ID, complete payload and a recognized positive job state. An enqueue response alone is insufficient. Lost lease COMMIT responses cause no enqueue; lost enqueue or publication responses retain uncertainty until authoritative positive readback confirms the same identity. Expired leases become `UNKNOWN`; negative readback never resets or republishes UNKNOWN work. Shadow UNKNOWN operations remain closed and cannot lease.

Broker preparation now requires persisted `PUBLISHED` state, non-null immutable payload bytes and an exact publication receipt. Its attempt binds optional focus by digest, and a SQL insertion guard enforces the publication/focus fence. `verifyDispatch` provides a second, closed-by-default consumer fence that checks the current queue snapshot against that persisted authority. The fast-consumer fixture cannot prepare or pass this fence before publication confirmation. The legacy worker is not wired to this new path: activation still requires its broker-mode bridge to apply the fence and replace the legacy paid-start path as one coordinated change.

The restricted PostgreSQL/Redis fixture covers concurrent and duplicate publication, same-ID spoofed payloads, changed scope, full focus identity, shadow and legacy quarantine, abandoned leases, lost lease/publication COMMIT acknowledgements, lost enqueue acknowledgements, negative and later positive readback, the fast-consumer fence and role/key denial. Queue and new outbox COMMIT faults are injected after the actual effect at the API response boundary; the existing broker fixture also drops a real PostgreSQL COMMIT response over its local relay. These checks do not establish managed-service failover, hosted queue durability, production role membership, supervisor authentication or provider settlement. A private queue readback receipt is not a supervisor signature or authority to start paid work.

Task 2 remains incomplete. Enforced shared admission across callers, production queue transport and worker integration, authenticated command leasing and receipt ingestion, idempotent provider settlement and coordinated replacement of the legacy paid-start path remain required before activation. Production admission stays held.

### Closed worker processor bridge

The actual worker entrypoint now uses `createWorkerScanJobProcessor`. Its default is closed. `workerAuthorityStartup` is the one immutable, server-owned selection for both job execution and queue lifecycle; it explicitly retains `legacy` with `existing-production-baseline` compatibility. No environment flag, queue field, client grant, payer or epoch can select the candidate. This source selection preserves the deployed baseline; it is not evidence that broker configuration has been installed or deployed.

A broker candidate requires an explicitly installed private broker/publication client and authority record. The installer must verify issuer qualification, exact product/image/engine tuple, current epoch, worker grant and expiry over protected IPC. Missing, invalid, expired, revoked or uncertain qualification stays closed. The worker validates the whole untrusted job, stored immutable plan, current workspace/target, creator/delegated permission and sponsor entitlement without invoking legacy terminal-status or slot-release mutations. The reviewed outbox fence requires the exact positively published job identity and payload, including focus, followed by qualification revalidation. These read-only snapshots are diagnostic; they do not authorize preparation.

The candidate uses the persisted operation ID for broker status and cancellation. Duplicate/restarted delivery observes that same operation; a lost acknowledgement is retained and never falls back to legacy execution, settlement or automatic requeue. The worker client exposes no prepare, paid-start or unmetered-start method. A queued operation with valid publication now calls broker `prepare`, whose READ COMMITTED transaction re-locks the operation, re-reads the live grant FOR SHARE and runs the SQL authority function; the worker's earlier member/permission/delegation/sponsor snapshots are advisory and a revocation between snapshot and write is rejected by that transaction. A committed attempt is retained as `BROKER_DISPATCH_PREPARED` because executor and provider dispatch are still not installed. The adapter still exposes no paid-start or unmetered-start method. Even a reported `PREPARED` state stays blocked until an authenticated supervisor receipt and its persisted matching transition can be consumed through a reviewed production adapter. Cancellation addresses only an existing persisted attempt through broker `stop`; uncertainty retains its holds.

Preparation remains structurally closed because the worker's current membership, permission, delegation and effective sponsor checks run before asynchronous queue/publication/qualification work and outside the broker's independent preparation transaction. The canonical SQL scope digest binds stored scan identity and delegation version; it does not bind the current membership, live connection status/scope or effective sponsorship decision. An atomic authority/version fence must be integrated with broker preparation and the corresponding revocation paths while preserving lock order before PREPARE can be exposed. A final out-of-transaction recheck would still race and is not an activation condition. Concurrent delivery/revocation tests change member, permission, delegation and sponsor authority after the initial admission snapshot and before publication validation returns; none can invoke PREPARE or either start path. These tests prove closure, not transactional revocation qualification.

Legacy queue reconciliation is guarded by the same immutable startup selection. Closed, broker and invalid modes cannot mark orphaned scans failed, release their slots or remove queue jobs through the legacy lifecycle. Until a broker-aware reconciliation/receipt bridge exists, that mode reports the lifecycle hold and performs no legacy mutation. The local worker tests cover spoofed jobs, unavailable publication/qualification, permission/target/delegation revocation, duplicate and restart identity, lost status/stop responses, startup mode capture, cancellation and both execution/lifecycle fallback denial. They do not qualify protected IPC, issuer signatures, production role grants, atomic preparation authority, real supervisor execution, provider integration or terminal settlement.
