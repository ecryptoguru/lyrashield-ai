## Executive summary

**15 confirmed findings: 0 Critical, 3 High, 12 Medium.** 34 items remain under
"Needs Verification" (medium-confidence or deployment-dependent, deliberately not
reported as vulnerabilities), plus 3 hardening notes.

The three High findings:

| ID | Domain | Summary |
|----|--------|---------|
| **VULN-A-001** | Authorization | Workspace-bound API keys and OAuth tokens read *other* workspaces on routes/dashboard pages that check membership only — cross-tenant read of targets, projects, member PII |
| **VULN-A-002** | Authorization | OAuth bearer sessions bypass credential-type rejection — a read-scoped or delegated token can mint a durable `lsk_` write key, publish public scorecards, and act on the creator's affiliate payout method |
| **VULN-C-001** | Money | Affiliate 12-month commission cap is unreachable dead code — every renewal mints a full commission for the life of the subscription |

A-001 and A-002 share one root cause: `requireWorkspaceAccess` enforces credential
workspace-binding but not the OAuth scope split, and several routes never call it.
Both were re-verified in source during consolidation. C-001 is a confirmed
dead-code defect (`isFirstPayment` has no production writer) with direct financial
impact; cash realization is currently gated by the admin-disabled payout path, but
the liability ledger accrues unconditionally.

The 12 Medium findings cluster into: supply-chain integrity gaps in CI/CD and the
distributed scan workflow (H-001..H-004, E-001, E-002), desktop/Tauri resilience
and license-enforcement issues (F-001..F-004), a fail-open secure-cookie
derivation (I-001), and a live-probe finding that marketing content is served
over plaintext HTTP without redirect (P-001).

No critical or high-confidence injection, RCE, SSRF, auth-bypass, or RLS-failure
vulnerability was identified. The architecture's central invariants — RLS scoping,
webhook signature verification, idempotent money paths, evidence integrity, fix-PR
approval binding, and platform-admin elevation — were tested against their
implementations and held.

## Findings

### VULN-A-001 — High — Workspace-bound credentials read other workspaces on membership-only routes and dashboard pages

- **Location:** `apps/web/src/app/api/targets/route.ts:273-344`,
  `apps/web/src/app/api/projects/route.ts:81-136`,
  `apps/web/src/app/api/team/route.ts:328-397`,
  `apps/web/src/lib/cache.ts:15-41` + `workspace-selection.ts:3-13` feeding every
  `app/(dashboard)/**` page; same defect via `GET /api/v1/targets` and
  `GET /api/v1/projects` re-export shims.
- **Confidence:** High. **Threat actor:** T2.
- **Issue:** `getSession()` falls back to `getBearerSession()`, which populates
  `session.apiKey.workspaceId` / `session.oauth.workspaceId` while `session.userId`
  is the credential's backing user. These routes accept an attacker-controlled
  `workspaceId` and check only `workspaceMember` for `session.userId` — the
  documented binding invariant ("a key minted for workspace A must never
  authorize workspace B", `session.ts:314-316`, enforced at `:317-322`) is never
  invoked. The dashboard variant resolves the active workspace from the unsigned,
  client-settable `activeWorkspaceId` cookie filtered by user memberships;
  `session.apiKey`/`session.oauth` are never consulted.
- **Impact:** A credential bound to workspace A whose backing user is also an
  active member of B reads B's target inventory (URLs, `apiSpecUrl`,
  `repoFullName`, environment), project metadata + `riskScore`, full member
  roster **with emails and pending-invitation emails** (PII), and all rendered
  dashboard pages (findings, scans, reports, billing, settings). PostgreSQL RLS
  does **not** mitigate: the Prisma extension binds `app.current_workspace_id`
  from the query's own attacker-chosen `workspaceId`. Stale-key amplification: a
  key keeps working after its creator leaves A and silently reads the creator's
  remaining workspaces.
- **Evidence:** membership probe then `findMany({workspaceId})` at
  targets:286-311 / projects:93-113 / team:340-392; `cache.ts:28-31`
  `selectActiveWorkspaceId(memberships, cookieStore.get("activeWorkspaceId"))`;
  `workspace-selection.ts:5-9` returns `requestedWorkspaceId` on membership match;
  correct pattern for contrast at `workspaces/route.ts:28-39,129-131`.
  Directly re-verified in source during consolidation.
- **Fix:** Route every workspace-scoped read through
  `requireWorkspaceAccess(workspaceId)`; where `getSession()` is retained, add
  explicit `session.apiKey.workspaceId !== workspaceId → 403` /
  `session.oauth.workspaceId !== workspaceId → 403`; clamp
  `getCachedWorkspaceContext` to the bound workspace when a credential session is
  present.
- **v16 overlap:** none.

### VULN-A-002 — High — OAuth bearer sessions bypass credential-type rejection: read/delegated tokens mint durable `lsk_` write keys and publish public scorecards

- **Location:** `apps/web/src/app/api/api-keys/route.ts:25-30,56-67` (GET/POST),
  `api-keys/[id]/route.ts:18-23` (DELETE), `targets/[id]/scorecard/route.ts:16-20`,
  `scorecards/[id]/route.ts:16-19`, `workspaces/active/route.ts:25-29`,
  `affiliates/api/payouts/method/route.ts:34-73`,
  `affiliates/api/payouts/request/route.ts:13-44`.
- **Confidence:** High. **Threat actor:** T2.
- **Issue:** `requireWorkspaceAccess` enforces workspace binding + membership/role
  only; the read/write scope split and delegated-operation grants live
  exclusively in `requirePermission` (`session.ts:356-380`). Every caller that
  hand-rolls the remaining check tests only `session.apiKey` and forgets
  `session.oauth`. `withCookieMutation` skips the same-origin gate for Bearer
  requests by design, so an OAuth token flows straight through — even on the
  api-keys routes whose docstring promises browser-only management.
- **Impact:** An OAuth token with only `lyrashield.read` — or a delegated
  `agentConnection` constrained by `allowedOperations`/`allowedTargetIds` —
  whose subject is an ADMIN member mints a durable `lsk_` key with
  `scopes: ["read","write"]` (`createApiKey` at `:61-67`, `rawKey` returned once).
  That key satisfies `requirePermission`'s write check across the whole workspace
  API with no connection-level grant limits — self-serve privilege escalation
  plus a persistent credential that survives connection revocation. A
  read-scoped token held by a PUBLISHER can also create **public unauthenticated
  `/score/{slug}` scorecard shares** (externally visible disclosure from a read
  grant), and act on the creator's affiliate payout method / payout requests —
  money-adjacent actions outside the credential's contract.
- **Evidence:** `api-keys/route.ts:57-59` — `if (session.apiKey) → 403`, no
  `session.oauth` branch (re-verified in source); `session.oauth.workspaceId`
  binding at `session.ts:87-117,320-322`; correct both-types rejection for
  contrast at `connection-auth.ts:7`.
- **Fix:** Reject `session.oauth` alongside `session.apiKey` on api-keys and
  affiliate mutation routes; on scorecard publish/revoke and
  `workspaces/active`, call `requirePermission` with a mutating permission or
  extend the check to `session.oauth?.scopes.includes("lyrashield.write")` plus
  delegated-operation gating.
- **v16 overlap:** none (`e40a945b` hardens adjacent consent code, not these
  checks).

### VULN-C-001 — High — Affiliate 12-month commission cap is unreachable dead code; every renewal mints a full commission for the life of the subscription

- **Location:** `packages/affiliate/src/commission/engine.ts:275-313`; producers
  `packages/affiliate/src/webhook-dispatch.ts:185-187`,
  `packages/billing/src/domain-events.ts:408-411`; metadata stamped at
  `apps/web/src/app/billing/checkout/route.ts:129-136`.
- **Confidence:** High (verified end-to-end; consolidation grep confirms
  `isFirstPayment` writers exist only in `*.test.ts`/e2e specs). **Threat
  actor:** T2 (APPROVED affiliate; self-referral check is email-equality only).
- **Issue:** `onOrderPaid` creates the `AffiliateSubscription` row — which
  carries `firstPaidAt`/`capEndsAt` — only inside `else if (isFirstPayment)`
  (engine.ts:289). The flag is read from event metadata but production checkout
  metadata never stamps it. `providerSubscriptionId` is populated, so the
  `findUnique` runs on every event and always misses → `capEndsAt` stays null →
  the `capMonths`/12-month expiry branch (engine.ts:316-364) is unreachable.
- **Impact:** The contractual cap (`capMonths` default 12; public affiliate copy)
  is unenforced — a referred LAUNCH_ASSURANCE annual subscription ($4,188) mints
  ~$1,047 commission **every year, forever**; monthly plans mint on every
  `subscription.charged` up to the 100-year `total_count`. Commissions flow
  `PENDING → AVAILABLE` hourly and accrue as payable liability; cash realization
  is currently gated by the admin-disabled payout path but pays out once that
  gate opens. Side effects: `activeReferrals` never increments (30% tier
  unreachable — affiliates *under*-paid at scale), `Conversion.subscriptionId`
  always null, clawback decrement unreachable.
- **Evidence:** engine.ts:289 (`else if (isFirstPayment)`);
  domain-events.ts:408; checkout metadata shape has no `isFirstPayment`; repo
  grep confirms no production writer.
- **Fix:** `upsert` `AffiliateSubscription` on `providerSubscriptionId` with
  `capEndsAt = firstSeen + capMonths` whenever a paid event arrives (the unique
  key makes it race-safe), then apply the expiry branch on subsequent events;
  backfill from earliest `Conversion.occurredAt`; optionally stamp
  `isFirstPayment` in checkout metadata for determinism.
- **v16 overlap:** none.
