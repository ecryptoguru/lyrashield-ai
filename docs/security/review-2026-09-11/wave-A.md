# Wave A — HTTP surface, authn/authz, public endpoints

- **Baseline:** `main` @ `3b289a43` (dedupe manifest: `docs/security/review-2026-09-11.v16-dedupe.md`; v16 head `3fc40597`)
- **Files reviewed:** ~115 (all API route handlers incl. `/api/v1/*` re-exports, dashboard/affiliate pages, auth/session/OAuth/RLS packages, webhook validators, rate-limit/origin helpers, and the dedupe manifest)
- **Findings:** 2 (both High confidence) + Needs Verification items

## Findings

### [VULN-A-001] Workspace-bound API keys and OAuth tokens read other workspaces on routes/pages that check membership only (Severity: High)

- Location: `apps/web/src/app/api/targets/route.ts:273` (membership check :286-294); `apps/web/src/app/api/projects/route.ts:81` (:93-101); `apps/web/src/app/api/team/route.ts:328` (:340-348); `apps/web/src/lib/cache.ts:15-41` + `apps/web/src/lib/workspace-selection.ts:3-13` feeding every `app/(dashboard)/**` page (`dashboard/page.tsx:53-59` pattern); same defect exposed via `GET /api/v1/targets` and `GET /api/v1/projects` re-exports.
- Confidence: High
- Threat actor: T2
- **Issue:** `getSession()` (`packages/auth/src/session.ts:125-143`) silently falls back to `getBearerSession()`, so an `Authorization: Bearer lsk_…` key or OAuth token produces a session carrying `session.apiKey.workspaceId` / `session.oauth.workspaceId`. The documented invariant — _"a key minted for workspace A must never authorize workspace B, even when the key's creator is a member of both"_ (`session.ts:314-316`) — is enforced only inside `requireWorkspaceAccess`/`requirePermission` (`session.ts:317-322`). These routes instead accept an attacker-controlled `workspaceId` query param and check only `workspaceMember` for `session.userId`. The dashboard makes it worse: `getCachedWorkspaceContext` resolves the active workspace from the **client-settable, unsigned `activeWorkspaceId` cookie** filtered by user memberships — `session.apiKey`/`session.oauth` are never consulted.
- **Impact:** A credential bound to workspace A whose subject user is also an active member of workspace B reads workspace B's:
  - `GET /api/targets?workspaceId=B`: target URLs, `apiSpecUrl`, `repoFullName`, branch, environment, status, scan/finding counts (also via `/api/v1/targets`).
  - `GET /api/projects?workspaceId=B`: project names, descriptions, `riskScore`, counts (also `/api/v1/projects`).
  - `GET /api/team?workspaceId=B`: full member roster with names/emails/roles plus **pending invitation e-mail addresses** (PII).
  - `GET /dashboard/**` with `Cookie: activeWorkspaceId=B`: rendered findings, scans, reports, billing, settings, connections, approvals, launch-readiness pages for B.
  - Typical scenario: an admin belonging to workspaces A and B mints a CI/contractor key scoped to A; the key holder now reads B's security posture and member PII despite the credential contract.
- **Evidence:** `GET /api/targets` → `getSession()` (line 273) → `prisma.workspaceMember.findUnique({workspaceId, userId: session.userId})` (286-294) → `prisma.target.findMany({where: {workspaceId, …}})` (298+) returning `url`, `repoFullName`, `environment`. Identical structure in `projects/route.ts` and `team/route.ts`. `cache.ts:28-31` calls `selectActiveWorkspaceId(memberships, cookieStore.get("activeWorkspaceId")?.value)`; `workspace-selection.ts:5-9` returns `requestedWorkspaceId` whenever it matches any membership. All ~22 `(dashboard)` pages consume this context. Correct handling exists for contrast in `workspaces/route.ts:28-39` (rejects bound creds) and `:129-131` (filters list to the credential's workspace).
- **Fix:** Route every workspace-scoped read through `requireWorkspaceAccess(workspaceId)` (or `requirePermission`) so `session.apiKey`/`session.oauth` binding is enforced; where `getSession()` is retained, add the explicit `session.apiKey.workspaceId !== workspaceId → 403` / `session.oauth.workspaceId !== workspaceId → 403` checks. In `getCachedWorkspaceContext`, clamp the selected workspace to `session.apiKey?.workspaceId ?? session.oauth?.workspaceId` when a credential session is present (cookie choice must intersect the bound workspace).
- v16Overlap: no — `packages/auth/src/session.ts` is v16-touched (+5, interaction only); the vulnerable routes/`cache.ts` are unchanged on v16 per the manifest.

### [VULN-A-002] OAuth bearer sessions bypass credential-type rejection and write-scope enforcement — read/delegated tokens can mint durable `lsk_` write keys and publish public scorecards (Severity: High)

- Location: `apps/web/src/app/api/api-keys/route.ts:25-30` (GET), `:56-67` (POST mint); `apps/web/src/app/api/api-keys/[id]/route.ts:18-23` (DELETE revoke); `apps/web/src/app/api/targets/[id]/scorecard/route.ts:16-20`; `apps/web/src/app/api/scorecards/[id]/route.ts:16-19`; `apps/web/src/app/api/workspaces/active/route.ts:25-29`; account-scope exposure at `apps/web/src/app/affiliates/api/payouts/method/route.ts:34-73` and `…/payouts/request/route.ts:13-44`.
- Confidence: High
- Threat actor: T2
- **Issue:** `requireWorkspaceAccess` enforces credential _workspace binding_ and membership/role only — it deliberately does **not** enforce the read/write scope split or delegated-operation grants (those live exclusively in `requirePermission`, `session.ts:356-380`). Every caller that hand-rolls the remaining check tests only `session.apiKey` and forgets `session.oauth`. `withCookieMutation` (`lib/api-auth.ts:67-80`) skips the same-origin gate for Bearer requests by design, so an OAuth token flows straight through. The api-keys routes even document _"ADMIN+ browser session … API keys cannot mint or list other API keys"_ — yet only `session.apiKey` is rejected; `session.oauth` is accepted.
- **Impact:**
  - `POST /api/api-keys` (`:56-67`): an OAuth access token with **only `lyrashield.read`** — or a delegated `agentConnection` constrained by `allowedOperations`/`allowedTargetIds`/`allowedProfiles` — whose subject is an ADMIN member of the bound workspace mints a durable `lsk_` key with caller-chosen `scopes: ["read","write"]` (`createApiKey` at `:61-67`). That key then satisfies `requirePermission`'s write check (`session.ts:358-364`) across the entire workspace API (scans, retests, fix proposals/PRs, reports) with **no connection-level grant limits** — self-serve privilege escalation plus a persistent credential that survives connection revocation. `GET` lists key metadata; `DELETE /api/api-keys/[id]` revokes arbitrary keys.
  - `POST /api/targets/[id]/scorecard` (`:17` checks only `session.apiKey`): a read-scoped OAuth token held by a PUBLISHER-role member creates a **public, unauthenticated `/score/{slug}` scorecard share** — externally visible disclosure from a read grant. `DELETE /api/scorecards/[id]` revokes shares the same way.
  - `POST /api/workspaces/active`: same apiKey-only check; effect confined to cookie state (low impact, same defect).
  - Affiliate `payouts/method` + `payouts/request`: a workspace-bound key/OAuth token acts on the _creator's_ affiliate account — overwrite the stored payout method (`fundAccountId`/payeeId; verification is reset, bounding theft) and trigger payout requests to a previously verified method — money-adjacent actions far outside the credential's workspace contract.
- **Evidence:** `api-keys/route.ts:57-59` → `if (session.apiKey) { …403… }` — no `session.oauth` branch; `createApiKey({workspaceId, scopes, createdById: session.userId})` at `:61-67` returns `rawKey` once (`:82`). OAuth context reaches here because `getBearerSession` (`session.ts:87-117`) maps OAuth tokens to `session.oauth`, and `requireWorkspaceAccess` (`:320-322`) passes when `session.oauth.workspaceId === workspaceId`. Delegated-grant and scope enforcement exists only in `requirePermission` (`:356-380`), which these routes never call. Contrast: `connection-auth.ts:7` correctly rejects **both** credential types.
- **Fix:** On api-keys routes reject `session.oauth` alongside `session.apiKey` (browser-session-only management, matching the docstring). On scorecard publish/revoke and `workspaces/active`, either call `requirePermission` with a mutating permission or extend the scope check to `session.oauth?.scopes.includes("lyrashield.write")` and add delegated-operation gating where applicable. Gate affiliate mutations to browser sessions (`if (session.apiKey || session.oauth) → 403`).
- v16Overlap: no — `e40a945b` (OAuth client identity/connection records) touches adjacent consent/connection code but does not add `session.oauth` rejection to these routes; `api-auth.ts` v16 interaction noted, defect confirmed on `main`.

## Needs Verification

- **`getClientIP` trusted-header trust** (`apps/web/src/proxy.ts` / `TRUSTED_PROXY_IP_HEADER`, rightmost-element read): if the configured header can reach the origin un-stripped (direct origin access bypassing Cloudflare, or a proxy that forwards client-supplied values), per-IP buckets are spoofable and the in-memory fallback Map grows unboundedly under synthetic IPs. Exploitability is deployment-dependent (origin lockdown/mTLS); rate buckets for the expensive paths reviewed are workspace-keyed, limiting blast radius. Confirm the origin only accepts Cloudflare-mTLS traffic before classifying.
- **`session.activeWorkspaceId` / `pendingAgentConnectionId` as `input: true` session fields:** if Better Auth's update-session endpoint accepts client writes directly, `verifyOAuthBearer`'s device fallback (`packages/auth/src/oauth.ts:144-158`) trusts `session.session.activeWorkspaceId` as the OAuth workspace claim. Downstream membership checks (`requireWorkspaceAccess` → `getWorkspaceMembership`) still gate data access, so no tenancy bypass was identified — but the field's client-writability wasn't fully traced through the Better Auth plugin surface.
- **Affiliate `requestPayout` semantics** (`@lyrashield/affiliate`): a workspace credential triggering `payouts/request` to a _previously verified_ method may execute real money movement; whether operator approval intervenes before disbursement needs tracing into the provider payout path.
- **User-scope resources via workspace credentials:** `PATCH /api/onboarding`, `notifications/preferences`, `referrals/claim` accept Bearer credentials and mutate the _creator's_ user-level state (onboarding pointers, notification prefs, referral attribution). Membership/ownership checks hold and no cross-user access was found; whether a workspace-bound credential _should_ act on user-scope state is a design question, not a confirmed vulnerability.
- **In-memory rate-limit fallback under Upstash outage:** cooldown/fallback semantics verified in code; whether sustained Upstash failure plus distributed app instances materially weakens `api`/`lite-scan` buckets is environment-dependent.

### Platform closure — 2026-09-11

- `VERIFY-A-001` is evidence-closed. Azure readback shows the authenticated app
  requires client certificates and rejects direct requests without one. The
  passive scanner uses direct Azure Container Apps ingress; Azure documents that
  it appends the authoritative client IP as the rightmost `X-Forwarded-For`
  value, matching `getClientIP`'s rightmost-only parser.
- `VERIFY-A-003` is evidence-closed for the current launch. Neither production
  origin has RazorpayX/Payoneer payout environment values or secrets, and
  `RAZORPAYX_PAYOUT_ADMISSION` defaults to `off`; the provider call is therefore
  unreachable. Provider/operator controls require a new review before admission
  is enabled.

## Verified safe (controls that held)

- **Credential binding where `requireWorkspaceAccess`/`requirePermission` is used** (`session.ts:308-383`): workspace equality for `apiKey`+`oauth`, active membership, role, read-scope allowlist fail-closed for new permissions, delegated-operation grants on mutating permissions. Correctly applied across targets POST, findings, retests, fix-proposals, agent-approvals (approve/deny), schedules, team PATCH/DELETE/invite (with role-ceiling `canGrantRole`, last-owner protection, membership lock), invitations/[id], GitHub repos/install.
- **Connection management**: `requireBrowserConnectionManager` (`connection-auth.ts:6-7`) rejects both credential types after `requirePermission(agent.act)`; pause/resume/revoke additionally re-check connection ownership or `agent.approve`; create binds signed consent state (HMAC, expiry, userId+clientId+scopes match) and validates `allowedTargetIds` against the workspace.
- **`/api/workspaces`**: POST rejects bound credentials; GET filters memberships to the credential's bound workspace — the correct exemplar.
- **CSRF/origin**: `withCookieMutation` resolves cookie-first (forged Bearer can't exempt a browser session) and `assertSameOriginMutation` fails closed on contradictory `sec-fetch-site`/`Origin` vs `NEXT_PUBLIC_APP_URL`; Bearer requests correctly skip browser-origin checks.
- **GitHub webhook**: raw-body `x-hub-signature-256` verification fails closed (missing secret/signature/prefix/length all reject before timing-safe compare), Zod payload validation, provider delivery-ID dedupe with unique-constraint arbitration, durable deferred loop-closure.
- **Billing webhooks**: Polar (Standard Webhooks, `id.timestamp.body` HMAC, 5-min tolerance, base64 canonicalization) and Razorpay (HMAC over raw body, current+previous secret rotation, bounded 15-day provider replay window, derived event identity fallback that never fabricates IDs) both fail closed; `WebhookEvent` insert-then-process + unique constraints + durable tracks + bounded retries.
- **GitHub install flow**: signed expiring state bound to workspace, `requirePermission` on the workspace, GitHub-side ownership/admin verification, enum-pinned return paths, uniqueness-guarded rebinding.
- **Platform admin**: exact-email allowlist + verified `PLATFORM_OPERATOR` + TOTP-enabled + recent elevation stamped on the server-side session, browser-cookie-only (Authorization or missing cookie → 401), same-origin enforcement, bounded windows, action nonces for critical mutations; affiliate admin mutations disabled pending atomic audit.
- **API-key service**: 256-bit `lsk_` keys, SHA-256 hash-only storage, narrow SECURITY DEFINER lookup, timing-safe compare, revoked/expired/deleted/malformed all fail closed.
- **OAuth**: issuer/audience-pinned JWT verification; workspace claim required; connection-bound tokens re-validate status/user/workspace/clientId/scopes/version/expiry; scope allowlist; loopback-only native redirect registration; HMAC consent state bound to user+client+scopes.
- **Invitation accept**: unguessable token + invited-email==account-email match, CAS consume, no demotion of active members.
- **Sync**: `hasSyncWriteAccess` + membership + resolved sync credential + `withWorkspaceRLS` + monotonic CAS cursor (rewind rejected) + forged `verified`/`FIXED` status rejection; cursor reads over URL params rejected (405).
- **Public surface**: share tokens stored/compared as SHA-256 hashes with revoked/expired fail-closed; badge SVGs use controlled grades + `escapeXml`; SSRF guard on target URL/apiSpecUrl; domain-verification status computed server-side.
- **Onboarding IDOR**: `workspaceId`/`targetId` foreign keys verified against membership before persist; optimistic `expectedUpdatedAt` concurrency.
