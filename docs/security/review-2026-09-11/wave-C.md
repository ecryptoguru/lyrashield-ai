## Findings

### [VULN-C-001] Affiliate 12-month commission cap is unreachable dead code — every renewal mints a full commission for the life of the subscription (Severity: High)

- **Location:** `packages/affiliate/src/commission/engine.ts:275-313`; producers at `packages/affiliate/src/webhook-dispatch.ts:185-187` and `packages/billing/src/domain-events.ts:408-411`; checkout metadata stamped at `apps/web/src/app/billing/checkout/route.ts:129-136`
- **Confidence:** High — verified end-to-end in code; `isFirstPayment` is set only in test files (`grep` confirms no production writer).
- **Threat actor:** T2 — an `APPROVED` affiliate (or an affiliate plus a colluding second account; the self-referral check is email-equality only, `fraud/selfreferral.ts`).
- **Issue:** `onOrderPaid` creates the `AffiliateSubscription` row — which carries `firstPaidAt`/`capEndsAt` — only inside `else if (isFirstPayment)` (engine.ts:289). `isFirstPayment` is read from `payload.isFirstPayment ?? meta.isFirstPayment` (webhook-dispatch.ts:185-187) and `facts.metaBag?.isFirstPayment` (domain-events.ts:408), but production checkout metadata contains only `{workspaceId, accountId, plan, interval, promoCode?, affiliate_id?, click_id?}` — the flag is never stamped. `providerSubscriptionId` *is* populated (normalized `subscriptionId` from the subscription entity), so the `findUnique` on `AffiliateSubscription.providerSubscriptionId` runs on every event and always misses. Consequently `capEndsAt` stays `null`, `isExpired` stays `false`, and every `subscription_renewed`/`subscription_paid` event creates a full-rate `PENDING` commission — the `capMonths`/12-month expiry branch (engine.ts:316-364) is unreachable.
- **Impact:** The contractual cap (program terms `capMonths` default 12, `DEFAULT_CAP_MONTHS`, and the public affiliate page copy) is unenforced. A referred LAUNCH_ASSURANCE annual subscription ($4,188) mints ~$1,047 commission **every year, forever**; a monthly Razorpay plan mints on every `subscription.charged` up to the 100-year `total_count` — vs an intended ~12 months. Commissions flow `PENDING → AVAILABLE` via the hourly `releaseCommissions` job and accumulate as a payable liability; cash realization is currently gated by the admin-disabled affiliate/payout path, but the ledger accrues unconditionally and pays out once that gate opens. Side effects of the same dead branch: `Affiliate.activeReferrals` never increments (30% tier unreachable — affiliates are *under*-paid at scale), `Conversion.subscriptionId` is always `null`, and clawback's `activeReferrals` decrement (clawback.ts:168-185) is unreachable.
- **Evidence:** engine.ts:280-313 (cap/subscription branch), engine.ts:289 (`else if (isFirstPayment)`), schema.prisma:2210-2222 (`AffiliateSubscription`, `capEndsAt` required), domain-events.ts:408 (`Boolean(facts.metaBag?.isFirstPayment)`), checkout route.ts:129-136 (metadata shape — no `isFirstPayment`), repo-wide grep: `isFirstPayment` appears only in `*.test.ts`/e2e specs.
- **Fix:** Create-or-load the `AffiliateSubscription` whenever `providerSubscriptionId` is present: `upsert` on `providerSubscriptionId` with `capEndsAt = firstSeen + capMonths` on create (first observed paid event *is* the first payment — the unique key makes the create race-safe), then apply the `capEndsAt < now → EXPIRED amount=0` branch for every subsequent event. Backfill `AffiliateSubscription` rows for already-tracked subscriptions from earliest `Conversion.occurredAt`. Optionally stamp `isFirstPayment: "true"` in checkout metadata for determinism.
- **v16Overlap:** false — not among the commits `6896d842`/`e0cd54fb` fixes (trial eligibility, RLS-blind reconciliation, renewal replay guard, downgrade sweep, scheduled-scan guard).

## Needs Verification

1. **Stale signed-event regression of subscription state** — `syncSubscription`'s upsert unconditionally overwrites `status`, `currentPlan`, `interval`, `currentPeriodStart/End`, `canceledAt` (sync.ts:171-178); there is no monotonic ordering guard (no `currentPeriodStart`-regression or `occurredAt`-freshness check). An out-of-order signed event (Razorpay's accepted 15-day replay window, provider redelivery after a 5xx, or `retryWebhookTrack` re-executing a stored payload) can regress `currentPeriodStart`, which widens the `cycleStart >= cycleStart` balance window (balance.ts:132-155) so prior-cycle *leftover* minutes re-enter the spendable balance, and can flip `canceled → active`. Impact is bounded by prior-cycle unused minutes and self-corrects on the next current event or the hourly downgrade sweep; no reliable tenant-controlled way to force provider re-ordering was found, so this is listed rather than reported.

2. **Mid-cycle plan change grants a second full pool without revoking the first** — the grant key is `{accountId}:{cycleStartIso}:{plan}` (grants.ts:33-39). A plan-change event (`subscription.updated`/`activated` with a different mapped product) at the same `cycleStart` mints the new plan's full pool while the old plan's grant remains counted (`cycleStart >=` filter), so e.g. LAUNCH_ASSURANCE→STARTER keeps the 6,000-minute grant. Trigger requires a provider-side plan change; the self-serve path appears unreachable today because `getPolarPortalUrl` passes `billingAccount.externalId` (a subscription id) as `customerId` to `customerSessions.create` (portal route + polar/client.ts) and Razorpay has no self-serve plan change.

3. **`MinutePack.workspaceId` `onDelete: SetNull` vs workspace-keyed credit/refund lookups** — `reverseRefund` resolves the pack by `{workspaceId, externalId}` using the workspace id from signed payment metadata (refund.ts:41-44, 57-61); after a workspace hard-delete the row's `workspaceId` is `NULL` (schema.prisma:1965), the compound-key lookup can never match, and the billing track dead-letters — refunded minutes remain spendable under the retained `accountId`. Symmetrically, a late `order.paid`/`payment.captured` for a pack whose workspace was deleted hits an FK failure on `minutePack.create` (packs.ts:96-106) — paid, never credited. No user-reachable workspace hard-delete exists in `apps/web` (account deletion removes the `User` row too), so this is latent for ops/support deletion flows or a future workspace-delete feature rather than presently attacker-triggerable.

## Verified safe

- **Webhook integrity:** Polar Standard-Webhook HMAC + 5-min tolerance and Razorpay HMAC-SHA256 over the raw body (current+previous secret) both validate before parsing/state change; event allowlists; `(provider, externalId)` uniqueness arbitrates duplicate deliveries; durable per-track execution with bounded retries and dead-lettering; `processed` is derived from required-track success only. Unsigned `X-Razorpay-Event-ID` affects bookkeeping dedupe only — monetary idempotency keys come from signed-body resource ids.
- **Catalog/quote binding:** provider product/plan ids resolve through `POLAR_PRODUCT_IDS`/`POLAR_LOCAL_PRODUCT_IDS`/`RAZORPAY_PLAN_IDS` with unknown ids failing closed; metadata must agree with the configured mapping; Polar `subtotal_amount` must equal catalog price exactly; Razorpay amounts are bound by an HMAC-signed quote (`provider|kind|workspaceId|accountId|catalogKey|amountMinor|currency`) with `paidAmount === quotedAmount` enforced.
- **Usage accounting:** `{workspaceId}:{scanId}:{phase}` unique idempotency; sponsor from persisted `Scan.createdById`/`session.userId` (never client input); workspace+account advisory locks in fixed order inside serializable transactions; conditional `remainingMinutes >= decrement` pack debits; failed scans unbilled; cancelled scans bill elapsed without the floor; uncertain-commit receipts never re-bill; `beforeCommit` ordering prevents charged-but-unrecorded and recorded-but-uncharged splits.
- **Overage:** LAUNCH_ASSURANCE-only, requires `spendLimitCents > 0`, integer cents at `$0.15/min`, spend cap enforced by conditional update at debit time (admission check mirrors but the debit is authoritative); complimentary rows can never receive a spend limit.
- **Packs:** `creditTopUp` idempotent on `(workspaceId, externalId)` + advisory lock; minutes come from `MINUTE_PACK_MAP`, never the payload; expiry job uses conditional updates; refund reversal zeros `remainingMinutes` with `{workspaceId}:{refundExternalId}` idempotency and a CAS on the observed balance.
- **Trial/grace:** one trial per account via durable `User.trialStartedAt` claim under `billing:${userId}` advisory lock with conditional `updateMany`; paid workspaces rejected inside the lock; grace capped at 15 min/cycle via conditional `graceUsedMs < cap` updates — cannot self-extend.
- **Refund evidence:** `refund_completed` is emitted only on provider-proven *cumulative full* refunds (Polar `status=refunded`; Razorpay `processed` + `refund_status=full` + `refunded == paid` + currency match); partials/unknowns are receipt-only.
- **Checkout/topup:** Zod-enum plan/pack selection, server-resolved provider ids, server-computed amounts, per-account rate limit + Redis NX checkout-claim (production fails closed, never in-memory); one active paid subscription per account enforced before creation.
- **Entitlement/admission parity:** `GET /api/scans/eligibility` is read-only and mirrors every POST gate; `assertScanAllowed` re-checks authoritatively at creation with `session.userId` as sponsor; governing-row selection (`resolveAccountBilling`) is deterministic, lapsed `canceled`/`past_due` terms collapse to `FREE` immediately, and `workspace.plan` is display-only.
- **Affiliate clawbacks:** keyed on `provider:externalId` matching the original conversion; full amount+currency equality required else manual review (and missing workspace binding throws → dead-letter, never silent pass); `REVERSED` is a terminal no-op on replay; >$200 auto-flags.
- **Payouts:** `ADMIN_ACTION_DISABLED` enforced even for elevated platform admins; self-service payout-method writes always reset `valid:false`/`verifiedAt:null`; eligibility requires verified method + `VERIFIED` tax + $100 floor + no active payout; `requestPayout` admits only `razorpayx` under `RAZORPAYX_PAYOUT_ADMISSION=public` and INR-only commissions; capture-only CAS (AVAILABLE→RESERVED) with convergent finalization and fail-closed ambiguity handling; RazorpayX send carries `X-Payout-Idempotency`/`reference_id = payoutId`; stuck-PROCESSING sweeps reconcile via provider status with CAS.
- **Attribution/referrals:** opaque hashed cookie tokens (`__ls_aff`), APPROVED-only resolution, signup/cross-device attribution rejects self-referral (userId + email) and never overwrites existing attribution; `referrals/claim` binds `session.userId` and rejects pre-existing accounts via `NEW_ACCOUNT_WINDOW_MS`; platform referral rewards are double-guarded by `FOR UPDATE` + idempotent `usageRecord` upserts per side.
- **Money types:** all persisted amounts are `Decimal(19,4)`/`Int` cents/minutes; no float rounding on persisted values anywhere in the reviewed production paths (only compile-time constants, `Number.isSafeInteger`-guarded paise conversions, and BigInt minor-unit math in the normalizer/RazorpayX provider).
- **Complimentary grants:** dry-run default, exact confirmation phrase, verified operator + audit workspace, refuses to overwrite paid rows, `provider="complimentary"` excluded from spend-limit/paid-plan paths, reversal soft-deletes grant+unconsumed pool records.
- **License fulfillment:** insert-first atomic claim on `provider:orderId` partial unique index; retrieval links are one-time, sha256-hashed, 7-day expiring, and consumed atomically (`retrievalTokenUsedAt` CAS + ciphertext wipe); raw keys never emailed or logged; team seat minimum enforced; subtotal-vs-seats binding validated.

**Non-security observation (not a finding):** `referral_bonus` UsageRecords are written by `qualifyReferralForWorkspace` but `GRANT_KINDS` only counts `pool_grant`/`trial_grant` (balance.ts:69) — the bonus never credits the usable balance (under-delivery, fail-closed); and cookie-only-attributed signups never reach `onOrderPaid` because subscription checkout never stamps `affToken`/`affiliate_id` from the `__ls_aff` cookie (only `promoCode` is resolved) — also under-delivery.
