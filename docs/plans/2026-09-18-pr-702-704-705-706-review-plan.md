## Confirmed defects

### F1 — P1: interactive Turnstile challenge becomes unreachable during booking (#704)

Evidence: `apps/marketing/src/components/myra/myra-session.ts:142–169`; `apps/marketing/src/pages/demo.astro:56,443–447,523` at the reviewed #704 head.

The new challenge host is inside `#demo-step-slot`. The first challenge binds the module-global widget to that host. Choosing a time hides that entire step. The subsequent email-code request calls `getTurnstileToken()` again, but the helper only selects a host when no widget exists. An interactive challenge therefore renders in the hidden slot-selection section. Even a second visible host does not help, because the existing widget is reused. If the first host is hidden on initial selection, `querySelector()` checks only that host and falls back to a zero-size, `aria-hidden` container.

A Chromium probe executed the actual TypeScript helper after type stripping, with a mocked Turnstile API. It minted a token, hid the slot section, exposed another host and requested another token. Result: one render call, original host invisible, second host visible. This establishes the DOM/lifecycle defect; it is not a live Cloudflare verification or calendar-booking receipt.

Plan:

1. Keep the demo challenge host outside the mutually exclusive booking steps or explicitly pass the active surface's host to the shared helper.
2. Check host visibility before every challenge; select a visible host from all candidates and recreate the widget when necessary. Do not use a permanently hidden fallback for an interactive widget.
3. Use a coherent Turnstile execution lifecycle. The helper explicitly calls `execute()` but currently leaves execution at the default render mode; use `execution: "execute"` if retaining explicit execution.
4. Handle expiry, failed script loads, retry and late callbacks explicitly. A timed-out attempt must not settle a later request. Keep server-side verification fail-closed.

Acceptance: forced-interactive testing completes slot selection, details, review, email verification and mocked booking; opening/closing the panel and switching steps cannot hide the active challenge. Cover blocked script, retry, timeout, expiry and widget teardown. Use mock calendar/mail services for automated tests.

### F2 — P2: single-flight token acquisition duplicates a single-use credential (#704)

Evidence: `apps/marketing/src/components/myra/myra-session.ts:129–133`. Callers include the session mint, demo email-code request, support-case composer and identity renderer.

`getTurnstileToken()` returns the same promise and token to independent callers. Sharing a session-bootstrap operation is correct; sharing the credential across separate credential-issuing requests is not. For example, overlapping demo and support identity-code requests receive the same token and only one can pass server verification.

The executable probe returned `samePromise=true`, `tokens=["token-1","token-1"]`, `executions=1`. Cloudflare documents that tokens are single-use and that execution and appearance are separate controls: [Turnstile widget configuration](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/).

Plan: retain deduplication around `ensureMyraSession()`, but serialize independent challenge acquisitions so each consumer receives its own fresh token. Use a small promise queue or per-operation widget handling; do not introduce a general task framework.

Acceptance: two bootstrap callers cause one session POST; two distinct identity operations receive different tokens and both can pass a mock validator that rejects token reuse. Failure of one queued attempt must not poison the queue.

### F3 — P2: the site-wide gate skips production-absolute internal links and cross-page fragments (#702)

Evidence: `apps/marketing/scripts/crawl-built-site.mjs:331` and the `localHrefs`/`anchorTargets` construction in `scripts/crawl-built-blog.mjs`.

The gate fetches the built site through localhost and passes that URL into `inspectHtml()`. That parser considers links internal only when their origin equals the supplied URL's origin. An absolute link to `https://lyrashieldai.com/broken` is therefore considered external during the CI preview and is never checked. The site gate also does not consume the cross-page `anchorTargets` already extracted by the parser.

The probe supplied 201 otherwise valid pages, a broken production-absolute internal link and a link from `/p0` to `/p1#absent`. The gate returned zero violations and `/broken` was never requested. Same-page missing fragments are already caught and must remain covered.

Plan: separate semantic site origin from transport/fetch origin. Classify links against the canonical site origin, map same-site requests back to the local preview and validate fragment targets using the already fetched page facts. Reuse `ids` and `anchorTargets`; avoid a second whole-site crawl.

Acceptance: relative and production-absolute broken links fail; valid absolute links are checked locally without contacting production; missing cross-page fragments fail; external URLs remain outside this internal-link gate; query strings and encoded fragments are handled intentionally.

### F4 — P2: failed child sitemaps silently reduce the gate's coverage (#702)

Evidence: `apps/marketing/scripts/crawl-built-site.mjs:138–154`; `apps/marketing/tests-browser/seo.e2e.ts:37`.

`sitemapPaths()` silently continues when a sitemap cannot be fetched. If another child still contains over 200 pages, the browser test's minimum count passes. The gate reports a green result for incomplete coverage rather than explaining the missing sitemap.

The probe used an index with two children: one served 201 valid URLs, the other returned 503. Result: `pageCount=201`, zero violations. This is a synthetic regression test, not a claim that the current production sitemap is incomplete.

Plan: propagate sitemap status/parse failures into explicit violations, retain the failed URL and status and bound fetch time. Keep the visited set for cycles. Where practical, compare the discovered route set with the existing route inventory rather than relying only on `>200`.

Acceptance: an unavailable, empty or malformed child fails even when another child has 201+ valid pages. Validate all advertised child sitemaps and report incomplete discovery separately from page violations.

### F5 — P2: the tablet activity chip covers Myra's Help button (#706)

Evidence: `apps/web/src/components/myra/myra-panel.tsx:378` and `apps/web/src/components/webmcp/webmcp-activity-drawer.tsx:76`.

Both controls now occupy `bottom-20` below `lg`; Help uses `right-4 z-40` and activity uses `sm:right-6 z-50`. Once there is a WebMCP receipt, the higher activity chip overlaps Help. The breakpoint change extends this problem into the 768–1023px tablet layout that this PR is intended to repair.

A Chromium layout probe used PR #706's existing built CSS and the exact source positioning classes at 768×1024. The rectangles overlapped and `elementFromPoint()` at Help's center returned the activity control. This was an isolated geometry test with representative button dimensions, not a fresh authenticated full-app session. Existing snapshots do not cover both controls being visible together.

Plan: give the two controls distinct positions or one small shared stack above the bottom navigation. Account for safe-area padding and the activity panel's expanded state. Do not fix this by increasing another z-index.

Acceptance: at 393, 768, 1023, 1024 and desktop widths, both controls remain visible and clickable with zero receipts, one receipt, a long tool name and an open panel. Keyboard focus and the navigation must remain reachable.
