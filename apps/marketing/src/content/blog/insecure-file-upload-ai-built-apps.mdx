Insecure file upload happens when an AI built app accepts files without strict server side validation and lets an attacker store executable or oversized content. In AI scaffolded code this often means trusting the file extension, skipping size checks and saving to a public folder. The risk ranges from stored XSS to remote code execution if the file is later served or executed.

This pattern shows up constantly in apps built with code generation tools. It also fits the broader set of pitfalls we cover in the [vibe coding security guide](/blog/vibe-coding-security-guide). AI assistants are great at wiring a drag and drop zone, a multipart handler and an S3 or local disk save in minutes, but they rarely add the verification layer that makes uploads safe for production. The same gap drives other authz issues like [IDOR in AI built apps](/blog/idor-ai-built-apps), where the generated route works but the permission check is missing.

The underlying problem is documented in official sources. [OWASP lists unrestricted file upload](https://owasp.org/www-community/vulnerabilities/Unrestricted_File_Upload) as a critical risk because an uploaded file can change application behavior. [CWE 434 defines unrestricted upload of file with dangerous type](https://cwe.mitre.org/data/definitions/434.html) as the root weakness and [PortSwigger explains file upload bypass techniques](https://portswigger.net/web-security/file-upload) that exploit trust in client side data.

## 1. How AI code generators build file uploads that fail open

Most AI built upload flows follow the same scaffold. A frontend component sends a File through fetch. A backend route calls something like multer, formidable or a framework parser. The handler checks `file.mimetype` or `file.originalname.endsWith()` and writes to `./uploads/` or a bucket with the original name.

That scaffolding misses three server side decisions. First, the content type check uses the client supplied header, not the actual bytes. Second, the size limit is either missing or set in the UI only, so a direct API call can bypass it. Third, the storage path is predictable and often inside the web root, which means the file can be requested directly after upload.

Vibe coded projects compound this because the prompt was usually about functionality, not security. A prompt like "add profile photo upload" yields working code fast, but not code that asks where the file should live, what types are allowed or how to serve it back safely. [MDN notes that file input accepts client hints only](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/file), which is why server side enforcement is required.

If you are reviewing an AI built app today, look for routes that call `fs.writeFile`, `createWriteStream` or cloud storage `putObject` without a preceding magic byte check or size validation in the same handler.

## 2. Common exploit patterns we see in AI scaffolded apps

The exploitation is not theoretical. Attackers chain small gaps.

One pattern is executable upload. An app allows images but only checks extension. An attacker uploads `shell.php.png` or `avatar.svg` containing script. If the server stores it under `/public/uploads/` and serves it with a sniffed content type, the file can execute or trigger stored XSS when viewed. SVG is especially risky because it can contain JavaScript.

Another pattern is path traversal via filename. AI code often uses `path.join(uploadDir, req.file.originalname)` without sanitization. An upload named `../../.env` or `..%2f..%2fconfig.js` can escape the intended folder. The result overlaps with [path traversal in generated code](/blog/path-traversal-generated-code), which is why restricting filename and folder handling matters.

A third pattern is size and resource exhaustion. Without server side limits, an attacker can upload gigabyte sized files or many files at once, filling disk or triggering high cloud bills. Missing rate limiting on the upload endpoint makes automated abuse easy. AI generated code often sets a UI limit like 5 MB but leaves the API route unlimited.

A fourth pattern is metadata abuse. Image parsers, PDF generators or thumbnail workers that process uploads without sandboxing can be abused with malicious EXIF or polyglot files. If the processing library is outdated, which happens often in AI generated `package.json`, the upload becomes an indirect supply chain vector.

## 3. What proper server side verification looks like

Fixing insecure upload requires verification at the server, not the client. Client side checks improve user experience but provide no security boundary.

Start with allow listing, not block listing. Decide which types you actually need. For most AI built apps that is a small set like JPEG, PNG, WebP and PDF. Everything else should be rejected. For each allowed type, verify the magic bytes on the server. Libraries like file type detection that read the first bytes are more reliable than extension or MIME header.

Next, enforce size twice. Once in the parser middleware as a hard limit that aborts the request and once in application logic before you write. Keep limits low by default, for example 2 to 5 MB for avatars and 10 MB for documents and make exceptions explicit per route.

Storage should be isolated. Save outside the web root with a randomized name, ideally a UUID and keep the original name only as metadata in your database. Set file permissions so the upload process cannot make the file executable. If you use S3 or R2, put uploads in a private bucket and serve through a signed URL or a controller that sets a safe Content Type and Content Disposition.

Delivery matters as much as storage. When you serve the file back, set `Content-Type` from your verified type, not from the stored client header and set `Content-Disposition: inline` or `attachment` explicitly. For images you want to render, consider re encoding or stripping metadata to remove script payloads. For SVG, treat it as high risk. If you do not need SVG, do not allow it. If you do, sanitize it with a server side sanitizer and serve with `Content-Security-Policy`.

Logging helps too. Log the verified type, size, final storage key and requester ID for every upload. That makes abuse detection feasible.

## 4. Minimal secure implementation checklist for vibe coded stacks

Use this table as a quick review for Next.js, Express, Remix or similar AI generated stacks. All of these checks should live on the server handler, not only in the React component.

| Fail Open Default                          | Safer Alternative In AI Built Code                                             | Why It Helps                                                                                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trust file extension or client MIME        | Verify magic bytes with a server library and map to an allow list              | Stops double extension and header spoof bypasses described in [OWASP file upload guidance](https://owasp.org/www-community/vulnerabilities/Unrestricted_File_Upload) |
| Save with original name to public folder   | Save with random UUID outside web root, store original name in DB only         | Prevents path traversal, predictable URLs and direct execution of uploaded files                                                                                     |
| No size limit or only UI limit             | Enforce parser limit plus app check, plus rate limit on the route              | Prevents disk fill, billing abuse and bypass by direct API calls                                                                                                     |
| Serve file with user supplied Content Type | Serve with verified type, set Content Disposition, strip metadata or re encode | Reduces stored XSS from SVG and polyglot files and aligns with [MDN safe content handling](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/file)     |

Implement this hardening in order. First, add the allow list and magic byte check. Second, add strict size and rate limits. Third, migrate storage to randomized names outside the web root. Fourth, harden serving with explicit headers. Each step can be shipped as a separate proposal requiring review, which keeps changes auditable.
