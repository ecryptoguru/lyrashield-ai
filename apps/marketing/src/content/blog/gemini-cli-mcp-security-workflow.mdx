## 1. Prerequisites and setup

You need Gemini CLI 0.9 or newer, Node 18 or newer, a LyraShield key prefixed `lsk_` for remote mode, and a GitHub repo for workflow setup. Gemini CLI stores MCP under `~/.gemini/settings.json` with key `mcpServers`, including `trust`, `includeTools`, and env expansion. The pattern is documented in the [Gemini CLI docs](https://github.com/google-gemini/gemini-cli) and summarized in the [Gemini CLI integration guide](/docs/integrations/gemini-cli). Restart Gemini CLI, then use its MCP tool list to confirm discovery. Review risk baselines via [OWASP Top 10](https://owasp.org/www-project-top-ten/) and advisory data via [OSV](https://osv.dev/). For protocol context, see [Model Context Protocol intro](https://modelcontextprotocol.io/docs/getting-started/intro). Validate the JSON with a linter after each edit, since a trailing comma or missing bracket will block all servers from loading.

## 2. Configure Gemini CLI MCP servers

Add entries to `~/.gemini/settings.json`. Use `trust` to control auto execution and `includeTools` to filter. The canonical reference is the [Gemini CLI integration guide](/docs/integrations/gemini-cli). Always link it as a markdown link, never a bare `/docs/integrations/gemini-cli` path.

The `includeTools` array is your blast radius control. Without it, the model sees every tool the server exposes, including write tools you may not intend to expose during a read only scan. By listing only `scan`, `lyrashield_list_targets`, `lyrashield_get_findings`, and `lyrashield_get_scan_status`, you prevent the agent from calling a write tool that could mutate your repo or push a branch. The `mcp.allowed` policy list works as a second gate at the CLI level. When present, only server names in that array load at all. If you add a server entry but forget its name in `mcp.allowed`, the CLI silently skips it, which is a common debugging trap.

Local stdio:

```json
{
  "mcpServers": {
    "lyrashield": {
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp"],
      "env": {
        "LYRASHIELD_API_KEY": "${LYRASHIELD_API_KEY}"
      },
      "trust": false,
      "includeTools": [
        "scan",
        "lyrashield_list_targets",
        "lyrashield_get_findings",
        "lyrashield_get_scan_status"
      ],
      "timeout": 120000
    }
  }
}
```

Remote HTTP:

```json
{
  "mcpServers": {
    "lyrashield-remote": {
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp", "--remote"],
      "env": {
        "LYRASHIELD_API_KEY": "${GEMINI_LYRASHIELD_CRED}",
        "LYRASHIELD_API_URL": "https://app.lyrashieldai.com/api/mcp"
      },
      "trust": false,
      "includeTools": ["scan", "lyrashield_list_targets", "lyrashield_get_findings"],
      "timeout": 120000
    }
  },
  "mcp": {
    "allowed": ["lyrashield", "lyrashield-remote"]
  }
}
```

Remote URL is [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp) with Bearer `lsk_`. The pinned npx form `npx -y @lyrashield/mcp` appears in both blocks. `$VAR` expansion and `mcp.allowed` policy are Gemini CLI specifics that control which servers run without prompting. For sibling editors, see the [Gemini CLI AI app security checklist](/blog/gemini-cli-app-security-checklist) which uses the same gate shape.

One env expansion gotcha worth knowing is silent auth failure. Gemini CLI strips env var names containing KEY, TOKEN, or SECRET from the subprocess environment before it spawns the MCP server, so a value exported as `LYRASHIELD_API_KEY` never reaches the server and every call returns a 401. The fix is to export the key under a name without those substrings, such as `GEMINI_LYRASHIELD_CRED`, and map `LYRASHIELD_API_KEY` to that reference in the server env block, as the config above does.

## 3. Verify the connection in Gemini CLI

Restart Gemini CLI and run `gemini mcp list` or ask "list MCP tools". You should see `lyrashield` with `scan` and `lyrashield_get_findings`. Run a status call: `gemini mcp call lyrashield lyrashield_get_scan_status`. If auth fails, ensure the credential var is exported in the shell that launched `gemini` (see the gotcha above for the naming rule). If tools do not appear, check `mcp.allowed` includes your server names and that `includeTools` does not hide them. For troubleshooting, the [Gemini CLI GitHub repo](https://github.com/google-gemini/gemini-cli) issues show common env visibility problems, and the [MCP spec](https://modelcontextprotocol.io/specification/2025-03-26) explains transport negotiation.

## 4. Run an inline check from the CLI

From Gemini CLI, ask it to scan the authorized target and return findings with their recorded evidence states, file locations, supporting evidence, and limitations. Use `lyrashield_scan_target`, then inspect results with `lyrashield_get_findings`; do not filter to “verified,” because independent verification requires a separate receipt.

The distinction between a finding with a recorded evidence state and raw lint noise matters for blocking merges. A finding with a recorded evidence state includes a concrete file path, a line number, and a proof snippet that demonstrates exploitability, such as a stored XSS finding that points to an unsanitized input rendered into the DOM along with a payload that executes in the browser. Raw lint noise flags a pattern without proof, such as a generic usage warning with no reachable input source. You block on the former and triage the latter.

Sample instruction for your Gemini CLI prompt library:

```md
Use lyrashield MCP:

- Scope diff vs main
- Return findings with recorded evidence states only with evidence and fix guidance
- Group as auth, injection, secrets, supply chain
- Record the intended remediation with `lyrashield_record_fix_proposal`; let the developer apply the code change.
```

`lyrashield_record_fix_proposal` records a remediation summary for review; it does not generate or apply a patch. After a developer makes the change, `lyrashield_verify_fix` queues a retest and returns a reference to poll. Keep scan IDs and SARIF artifacts explicit in the audit trail.

## 5. Wire the GitHub Action diff aware gate

Add `.github/workflows/lyrashield.yml` with SARIF upload so PRs are blocked consistently, as described in [GitHub docs for SARIF upload](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github).

```yaml
name: lyrashield diff gate
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: ecryptoguru/lyrashield-ai@v2
        with:
          fail_on_severity: HIGH
```

The workflow mirrors your Gemini CLI transport: same endpoint [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp) and same key shape. Diff mode keeps scans fast for agent driven branches by only scanning changed files rather than the full tree.

The SARIF file is uploaded to GitHub code scanning, where advisory results appear alongside other tools with file, line, and severity metadata. These local results do not carry hosted LyraShield finding IDs or evidence states; use a recorded scan for retained assurance evidence.

## 6. Add agent rules snippet

Save as `.gemini/rules/security.md` or your rules path.

```md
# Security rules for Gemini CLI

- Identify Target before scan: app root, routes, data class.
- Run LyraShield via MCP for changed files vs main.
- Apply the configured severity gate while preserving every finding’s evidence state and limitations.
- Record a fix proposal, apply the change outside LyraShield, then queue and poll the retest.
- Report scan ID and SARIF link in PR or CLI summary.
```

This keeps Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report consistent across local CLI and CI. ## 7. Why pair Gemini CLI with LyraShield

Gemini CLI gives you terminal native agent workflows, LyraShield adds recorded security evidence that is designed to travel from CLI to CI without custom scripts. The [vibe coding security guide](/blog/vibe-coding-security-guide) explains how AI built apps accumulate risks across injection, auth, and supply chain when verification is deferred. Pairing provides one loop from Target to Report with SARIF that GitHub code scanning understands per [docs.github.com on code scanning](https://docs.github.com/en/code-security/code-scanning/introduction-to-code-scanning). v1 is agentic pentest plus SCA plus secrets plus GitHub Action plus SARIF, Bounded scans, evidence states, fix-proposal recording, retest queueing, and SARIF are available now.

The value of a single transport across local and CI is consistency. The same MCP endpoint, the same `lsk_` key, and the same tool surface mean a finding you reproduce in your terminal is the same finding that blocks a PR in GitHub. SARIF output standardizes severity and location data so reviewers see results in the security tab they already use for CodeQL.
