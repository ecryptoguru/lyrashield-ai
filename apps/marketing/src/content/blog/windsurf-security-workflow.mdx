Windsurf with Cascade can edit many files and call external MCP tools quickly, so you must lock down MCP config, tighten project rules, gate dependencies and secrets and keep SARIF for every release. This workflow covers mcp_config.json with serverUrl, Cascade memories hardening and verifiable evidence. Baseline controls are in our [vibe coding security guide](/blog/vibe-coding-security-guide) with Windsurf specific checks below.

## Understand Windsurf and Cascade risk

Windsurf uses Cascade for agentic edits across files with tool awareness. Cascade can read workspace files, run commands and invoke MCP servers you configured. That speed is valuable but also means one prompt can add packages, expose data in logs or broaden network access without a clear record.

Typical AI inserted issues include debug endpoints that skip auth, error handlers that log secrets and new dependencies with install scripts. You need consistent weakness language so findings are triaged similarly across builders.

Map issues to common references. OWASP Top Ten at [OWASP Top Ten](https://owasp.org/www-project-top-ten/) captures injection and misconfiguration seen in AI generated back ends. Hardcoded credential patterns map to [CWE 798 for hard coded credentials](https://cwe.mitre.org/data/definitions/798.html). MCP transport and auth expectations are defined at [MCP specification](https://modelcontextprotocol.io/specification/2025-06-18) and [MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization). If you also ship with visual builders, our [Bolt app security checklist](/blog/bolt-app-security-checklist) shows similar permission ideas adapted to a different stack.

## Lock down MCP in mcp_config.json with serverUrl

Windsurf loads MCP servers from global ~/.codeium/windsurf/mcp_config.json for personal tools and local .codeium/windsurf/mcp_config.json for team shared servers. Both files use a mcpServers object. Remote servers use serverUrl field for HTTPS endpoints.

Secure example with zero raw secrets committed:

```json
{
  "mcpServers": {
    "lyrashield-local": {
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp"],
      "env": {
        "LYRASHIELD_API_KEY": "${LYRASHIELD_API_KEY}"
      }
    },
    "lyrashield-remote": {
      "serverUrl": "https://app.lyrashieldai.com/api/mcp",
      "env": {
        "LYRASHIELD_API_KEY": "${LYRASHIELD_API_KEY}"
      }
    }
  }
}
```

Hardening for review checklists:

* Prefer env var interpolation in env and never raw tokens in committed files. Validate in CI that no literal sk or lsk token appears in mcp_config.json.
* Keep global file for personal helpers and local file for team shared servers. Require explicit review for either file when a new MCP server appears. Treat new servers like new production dependencies with owner and review date.
* Limit server count per workspace. Each MCP server adds tool surface that Cascade can call, so only keep servers needed for current milestone.
* For remote MCP, confirm transport is HTTPS and auth uses Bearer from env. Short startup timeouts reduce hang risk and improve CI stability.
* For protocol reference, see [MCP spec overview](https://modelcontextprotocol.io). Supply chain context on packages loaded by MCP servers is at [OSV database](https://osv.dev). SARIF integration is at [GitHub SARIF support](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning).

Log which MCP servers were active for a feature branch in your pull request description. That single line helps reproduce permission problems and supports audit questions about external tools used during generation.

## Harden rules and workspace memories

Windsurf respects project rules in .codeium/windsurf/memories, optional muserules.md in repo root and global rules. Treat these as lightweight security policy that guides Cascade toward secure defaults.

Require these policy statements in your repo so generated code meets that bar from first commit:

Auth is required on all API routes handling user data, sessions or file access. No public bypass for local debugging remains after merge.

Input validation uses explicit libraries like zod or valibot for Node stacks, with tests for failure paths.

No shell exec with untrusted input. If exec is needed for image processing or similar, list allowed commands and sanitize args with allow list.

Package policy states allowed registries, need for lockfile audit before merge and reviewer requirement for new dependencies that introduce network access or native binaries.

Secret policy states env vars come from secret manager only, no secrets committed, no tokens pasted into Cascade summaries that get copied into tickets.

Version rules in git and require review on rules changes. When Cascade proposes broad multi file edits, split into smaller commits with tests for auth and upload paths so review stays effective.

Document the workflow in docs/contributing.md so new contributors know why rules exist and what evidence is expected per release.

## Gate supply chain and secrets

Windsurf Cascade solves tasks by adding dependencies, which creates supply chain risk if auto acceptance is allowed.

Run OSV checks at [OSV](https://osv.dev) and npm or pnpm audit in CI on every pull request, and block high severity vulnerabilities outright. Flag new packages with low weekly downloads, recent ownership change or install scripts that touch network or file system for manual review. Keep lockfile diffs readable by grouping dependency only commits separately from feature code.

For secrets, run a scanner such as gitleaks that can output SARIF and upload to GitHub code scanning. See [GitHub secret scanning SARIF](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning) and upload guidance at [GitHub SARIF artifact](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github). Check env .example and mcp_config.json examples for accidental tokens, and check editor logs and chat exports if pasted into issues, since tokens often leak via pasted logs.

Enforce both local pre commit hooks and CI scans. Local hooks give early feedback while CI is the gate. Require security owner review for any env file change or new MCP server addition, so token handling always gets a second set of eyes.

## Build verifiable release evidence with SARIF

Collect evidence you can point to in release notes without depending on memory or private chat logs.

Repeatable per release procedure:

1. Run lint, type check, secret scan and dependency audit locally and in CI.
2. Convert each tool output to SARIF where the tool supports it.
3. Upload SARIF to GitHub code scanning so findings surface in pull request checks.
4. Add docs slash security evidence entry with date, commit hash, active MCP servers, tools run and reviewers.
5. Store build and SARIF artifacts with release tag for later reference.

See overview at [GitHub code scanning](https://docs.github.com/en/code-security/code-scanning) and hardening ideas for web apps at [Next.js security](https://nextjs.org/docs/app/guides/data-security) and [Cloudflare fundamentals](https://cloudflare.com/learning/). These help frame header and auth review while your app specific verified findings remain in SARIF.

Keep evidence for several releases so you can show trend, exception closure and repeatability of controls. If you use remote MCP, record serverUrl and version used during generation so tool output drift can be reproduced.

| Control | Where configured | Verification signal |
| --- | --- | --- |
| MCP config | mcp_config.json with serverUrl and env refs | No raw keys in git, least servers enabled, changes reviewed in pull request |
| Rules | .codeium/windsurf/memories plus muserules | Auth and validation required, destructive commands denied, tests added |
| Dependencies | OSV plus audit in CI | High severity blocks merge, lockfile diff reviewed, exceptions tracked |
| Secrets | Secret scan plus SARIF upload | No tokens in repo or logs, env via manager, example files placeholder only |
| Evidence | GitHub code scanning plus evidence file | SARIF on PR and main, MCP list logged, release tag linked |

## Release gates and next steps

Before you ship a Windsurf built release, confirm gates.

* mcp_config.json files contain no raw tokens and only needed servers are enabled.
* Rules require auth and validation and forbid risky exec with untrusted input.
* Dependency and secret scans passed and SARIF uploaded on pull request and main.
* Auth, payment or file upload changes include tests and reviewer.
* Security evidence file updated per release tag with MCP list and date.
