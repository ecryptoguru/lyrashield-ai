To connect Goose to LyraShield, run npx lyrashield install goose so the CLI prints the YAML values to paste into the extensions map, then run npx lyrashield doctor to verify the connection and credentials. Goose is the open source agent from Block and uses a YAML extensions map in ~/.config/goose/config.yaml rather than a mcpServers key. This workflow covers the install, manual fallback, verification, an inline check, a CI gate, and a hints snippet.

The [vibe coding security guide](/blog/vibe-coding-security-guide) separates generated code from the controls that enforce what it may do. Wiring LyraShield into Goose puts release assurance inside the agent session, so a scan runs before a change reaches a pull request rather than only after. The steps below assume you have Node installed and an active LyraShield account.

| Step          | Command or file                       | Purpose                          |
| ------------- | ------------------------------------- | -------------------------------- |
| Prerequisites | Node 20 plus, git, LyraShield account | Prepare the environment          |
| Install       | npx lyrashield install goose          | Print YAML values to paste       |
| Manual path   | ~/.config/goose/config.yaml           | Fallback if CLI is unavailable   |

## 1. Meet the prerequisites

Install Node 20 or later, which the [Node.js release guide](https://nodejs.org/en/docs/) covers. Confirm git is configured for your repository. Create a LyraShield account at [lyrashieldai.com](https://lyrashieldai.com) if you do not have one, because the MCP server needs credentials to authenticate. Run npx lyrashield login to store your credentials in ~/.lyrashield/credentials.json, which is not committed to version control.

Goose does not use a rules file. Project specific instructions live in a .goosehints file in the project root, which is the main project level instruction source. Keep your credentials file outside the working tree, and never paste a token directly into a config file the agent can read.

## 2. Add the LyraShield extension

Run npx lyrashield install goose. The CLI prints the YAML values to paste into the extensions map in ~/.config/goose/config.yaml. The extensions map is a nested YAML structure, not a mcpServers key. A local extension uses type stdio with cmd and args. A remote extension uses type streamable_http with uri and headers. The [Model Context Protocol specification](https://modelcontextprotocol.io/) defines the transport and tool exposure contract.

If the CLI is unavailable, add the entry manually. This is the manual path, and it is exactly what the CLI prints. For a remote extension:

```
extensions:
  lyrashield:
    type: streamable_http
    uri: https://app.lyrashieldai.com/api/mcp
    headers:
      Authorization: Bearer lsk_YOUR_TOKEN
```

For a local stdio extension:

```
extensions:
  lyrashield:
    type: stdio
    cmd: npx
    args: -y @lyrashield/mcp stdio
```

Keep any headers or credentials in environment variables referenced by the config, never as literal strings in the YAML.

## 3. Verify the connection

Run npx lyrashield doctor. It checks that ~/.config/goose/config.yaml is valid, the extension entry is present, and your credentials resolve. If any check fails, the doctor reports the gap and the fix, so you can correct it before running a scan. A green doctor result means Goose can reach the LyraShield server and authenticate.

Restart your Goose session after editing the config file so the agent loads the new extension. Confirm the LyraShield tools appear in the session. If the tools are missing, check the type and uri spelling, the token, and whether the extension is enabled. The doctor does not run a scan; it only confirms the wiring. If a check fails, the doctor names the file, the field, and the expected value, so you can fix the gap without reading the full config. Run the doctor again after each fix until every check is green, because a partial fix can leave the server reachable but unable to authenticate.

## 4. Run an inline security check

With the connection verified, run npx lyrashield scan from your project root. The scan targets the repository, reviews the code for candidate issues, and records evidence in an immutable assurance record. Detected issues stay in a detected state until independent verification confirms the behavior, so a finding is a prompt to investigate, not a verdict. Read each finding in the session, note the file and line, and decide whether the candidate reflects a real weakness or a false positive that deserves a recorded dismissal. The assurance record holds both the confirmed issues and the dismissed ones, so a reviewer can see the full set of decisions, not just the open items.

Review the scan output in the session. If a candidate issue is real, a fix proposal is generated for review. Approval gated fix proposals require a human review before a patch reaches a pull request, so a fix is never automatic. ## 5. Gate pull requests with the GitHub Action

Add the LyraShield GitHub Action to your CI so every pull request is scanned. The action runs a diff aware gate, which means only changed code is scanned on each pull request, keeping the check fast enough to run on every push. Output is SARIF, which GitHub renders in the security tab. The [GitHub Actions documentation](https://docs.github.com/en/actions) covers workflow syntax and the [GitHub SARIF integration](https://docs.github.com/en/code-security) explains how findings appear. Store the LyraShield token as a repository secret rather than a variable, so it stays encrypted and masked in logs. Set the diff aware flag to true so the action scans only the lines a pull request changes, which keeps the gate fast on large repositories and avoids re-scanning untouched code on every run.

Add a workflow file named lyrashield.yml under the .github/workflows directory:

```
name: LyraShield
on:
  pull_request:
    branches: [main]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: ecryptoguru/lyrashield-ai@v2
        with:
          fail_on_severity: HIGH
```

## 6. Add a hints snippet to .goosehints

Tell Goose to use LyraShield before proposing a fix. Add a line to .goosehints in your project root:

```
Run the LyraShield scan tool before proposing a fix. Do not apply a patch until a human reviews the fix proposal. Keep detected issues in a detected state until independent verification confirms the behavior.
```

A hints file states intent. The approval gate enforces it. A prompt can be changed in a pull request or ignored under pressure, but a server side gate that blocks a patch until a human binds it to an approval cannot be talked past. That is the difference between stating a policy and holding one. Require a security owner for changes to agent configuration, and include .goosehints in normal code review and branch protection.
