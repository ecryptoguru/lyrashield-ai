Fastest path: run `npx lyrashield init` to auto-detect Kilo Code and write the correct entry, then `npx lyrashield doctor` to verify and `npx lyrashield login` to store credentials. The manual config below is what the CLI writes, kept for reference.

You can connect Kilo Code to LyraShield AI over MCP to get target aware scans, recorded evidence states, and fix proposals inside your normal agent loop without leaving the editor. In this guide you will configure the local stdio server using pinned npx -y @lyrashield/mcp plus the remote endpoint at https://app.lyrashieldai.com/api/mcp, verify tools are listed, run an inline check, and wire a diff aware GitHub Action gate with SARIF upload.

Vibe coding moves fast and security debt can accumulate when large batches of routes, components, and queries are generated in one pass. If your team uses Kilo Code to scaffold features, you want verification that matches that speed. A good starting policy is the [vibe coding security guide](/blog/vibe-coding-security-guide) which frames prompt hygiene, review checkpoints, and supply chain checks. For context on what to look for, see [OWASP Top 10](https://owasp.org/www-project-top-ten/) and [CWE Top 25](https://cwe.mitre.org/top25/), both of which confirm injection, broken access control, and vulnerable dependencies remain top risks in generated web apps.

When you generate code with an agent, you generate more attack surface than a human would in the same window. That is why early target aware scanning matters. The workflow below keeps scanning close to generation, then enforces a consistent gate in CI so main stays clean even when generation velocity spikes.

## 1. Prerequisites and workspace baseline

Start with Node.js 20 or newer which you can confirm via [Node.js docs](https://nodejs.org/en/docs), Git with pull request workflow, and a LyraShield API key in the form lsk\_... Set the key as an environment variable named LYRASHIELD_API_KEY and avoid pasting raw values into checked in files. Kilo Code resolves `{env:LYRASHIELD_API_KEY}` at runtime, so secrets stay out of kilo.jsonc.

Take stock of the app scope you want to protect. LyraShield combines bounded repository review, SCA, secrets scanning, a GitHub Action, and SARIF output. Findings retain their recorded evidence states; scan detection alone is not independent verification. Fix proposals and retests remain approval-gated, and PR execution remains unavailable until a server-generated patch can be bound to an exact approval. Read [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) for why stdio works locally and streamable HTTP fits remote hosting.

Quick sanity checks for the MCP package and env wiring:

```bash
node -v
npm view @lyrashield/mcp version
export LYRASHIELD_API_KEY=lsk_your_key_here
npx lyrashield doctor
```

For a concrete remediation checklist that mirrors your stack, keep a sibling reference such as [Kilo Code app security checklist](/blog/kilo-code-app-security-checklist) open while you implement. It helps you map a recorded finding to a specific fix pattern without guessing.

Also confirm that your repository has a clear target definition. LyraShield uses target as the unit of verification. That could be staging web, production API, or a preview deployment. Deciding the naming convention before you wire MCP avoids permission confusion later, especially when you add the remote server alongside local. Teams that name targets after deploy environments usually have the least confusion during triage, because a finding is instantly tied to where it was observed.

## 2. Configure LyraShield MCP server in Kilo Code

Kilo Code reads MCP servers from kilo.jsonc at project root or from the global file at ~/.kilo/kilo.jsonc under mcp.servers. Use type local for stdio and type remote for remote. Include permission globs, environment indirection, and tool allow lists.

```json
{
  "mcp": {
    "servers": {
      "lyrashield": {
        "type": "local",
        "command": "npx",
        "args": ["-y", "@lyrashield/mcp"],
        "env": {
          "LYRASHIELD_API_KEY": "{env:LYRASHIELD_API_KEY}"
        },
        "permissions": {
          "fs": ["read:./src/**", "read:./app/**", "read:./packages/**"],
          "net": ["allow:api.lyrashieldai.com"],
          "tools": [
            "lyrashield_scan_target",
            "lyrashield_get_findings",
            "lyrashield_list_targets",
            "lyrashield_get_scan_status",
            "lyrashield_generate_fix_plan",
            "lyrashield_record_fix_proposal"
          ]
        }
      },
      "lyrashield-remote": {
        "type": "remote",
        "url": "https://app.lyrashieldai.com/api/mcp",
        "headers": {
          "Authorization": "Bearer {env:LYRASHIELD_API_KEY}"
        },
        "permissions": {
          "tools": [
            "lyrashield_scan_target",
            "lyrashield_get_findings",
            "lyrashield_list_targets",
            "lyrashield_get_scan_status",
            "lyrashield_generate_fix_plan",
            "lyrashield_record_fix_proposal"
          ]
        }
      }
    }
  }
}
```

This satisfies the product requirement to pin stdio to npx -y @lyrashield/mcp and to expose remote at https://app.lyrashieldai.com/api/mcp via bearer header. The canonical reference lives in [Kilo Code integration guide](/docs/integrations/kilo-code). Keep hostConfigDiscovery style defaults off for deterministic clones and ensure permission globs cover only source roots you intend to share.

If you manage config centrally, store the global file at ~/.kilo/kilo.jsonc with the same shape and let projects inherit it, which gives platform teams consistent verification across many repos.

## 3. Verify connection and list security tools

Restart Kilo Code after editing the config. Open the MCP panel and expect lyrashield and lyrashield-remote to show connected with green status. If either shows disconnected, confirm that LYRASHIELD_API_KEY is exported in the shell that launched Kilo Code and that no corporate proxy blocks the remote endpoint.

Ask the agent to enumerate tools:

```text
Prompt: List MCP tools from lyrashield and lyrashield-remote.
Show transport type and tool names.
```

Expected result:

```text
Available MCP tools from lyrashield:
- lyrashield_scan_target(targetId, goal, mode)
- lyrashield_get_findings(targetId)
- lyrashield_list_targets()
- lyrashield_get_scan_status(scanId)
- lyrashield_generate_fix_plan(findingId)
- lyrashield_record_fix_proposal(findingId, summary)

Remote lyrashield-remote:
- lyrashield_scan_target, lyrashield_get_findings, lyrashield_list_targets
- lyrashield_get_scan_status, lyrashield_generate_fix_plan, lyrashield_record_fix_proposal
```

For supply chain background, skim [OSV database](https://osv.dev/) to see how dependency advisories are structured and [GitHub Actions docs](https://docs.github.com/en/actions) to understand how secrets and SARIF flows operate. These references help you interpret SCA results that surface alongside appsec findings. Seeing both servers list the same core tools confirms that auth propagates correctly for stdio and http.

## 4. Run an inline security check from your agent

With tools listed, run a focused scan from inside Kilo Code rather than switching to a dashboard. The intended core loop is Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report. Use a prompt that preserves evidence states instead of flattening every detection into a verified claim.

```text
Prompt for Kilo Code agent:
Scan target staging-lyrafin-web using lyrashield_scan_target.
Scope limit: src/app/api, src/lib/engines.
Return findings with their recorded evidence state, CWE, evidence snippet, file and line.
Include OWASP mapping when applicable.
Save report id for PR gate.
```

A good response contains finding id, severity, evidence state, file path, evidence, and suggested patch location. Prioritize independently verified findings while retaining detected and inconclusive items for triage. For context on categories, see [OWASP Top 10](https://owasp.org/www-project-top-ten/) and [CWE Top 25](https://cwe.mitre.org/top25/) again for category definitions and examples. Do not claim fixes, branches, or PRs exist unless the corresponding action completed.

This inline check is also where you catch secrets that were generated into sample env files. LyraShield v1 includes secrets scanning alongside SCA, so a single scan can surface both hardcoded credentials and vulnerable packages. When evidence points to a config file, rotate the secret first, then fix the code path that introduced it.

## 5. Wire a diff aware GitHub Action gate

Local scans catch issues early, but teams need PR level enforcement that only touches changed code. Wire the official GitHub Action in diff aware mode and upload SARIF for native annotations.

```yaml
name: lyrashield security gate
on:
  pull_request:
    paths:
      - "src/**"
      - "app/**"
      - "packages/**"
  push:
    branches: [main]

jobs:
  security:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - name: LyraShield diff scan
        uses: ecryptoguru/lyrashield-ai@v2
        with:
          fail_on_severity: HIGH
```

Require the security job in branch protection settings. The pairing of MCP for local dev plus the Action for CI mirrors the Model Context Protocol idea of keeping context close to the agent while enforcing policy in CI. See [GitHub Actions docs](https://docs.github.com/en/actions) for reusable workflows and [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) for transport details. Once required, developers cannot merge when findings meet the configured severity gate; that policy does not turn a detected finding into an independently verified one.

## 6. Add agent rules for consistent secure coding

Add a repo level rules file that Kilo Code reads on each run. This makes the workflow repeatable for teammates using vibe coding patterns.

```markdown
# Security rules for Kilo Code

- Before finishing a feature, call lyrashield_scan_target on changed scope.
- Surface findings with CWE, file evidence, and their recorded evidence state.
- For high severity findings, generate and record a fix proposal; do not claim a branch or PR was created.
- On every PR, ensure lyrashield security gate passed and SARIF uploaded.
- Reference OWASP Top 10 and internal vibe coding security guide in PR descriptions when relevant.
- Never include secrets in logs or code. Use {env:LYRASHIELD_API_KEY}.
```

Store the file as .kilo/rules.md or kilo.md in your repo root so it travels with the code. This turns the core loop into daily behavior and reduces the chance that a teammate forgets to run the check during rapid iteration. It also makes security expectations visible to code reviewers, because the same rules they see in the PR description are the rules the agent followed while generating the change.

| Stage       | What Kilo Code does                       | What LyraShield adds                                  | Verification signal                |
| ----------- | ----------------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| Generation  | Scaffolds routes and queries from prompts | N/A                                                   | Prompt review                      |
| Local check | Calls MCP tools from editor               | Target aware scan plus SCA plus secrets with evidence | Finding id with CWE and file path  |
| PR gate     | Pushes diff to GitHub                     | Diff aware scan plus SARIF plus fail on high          | GitHub check green and annotations |
| Remediation | Reviews and applies an approved proposal  | Recorded fix proposal and server-owned retest         | Retest outcome plus scan reference |
