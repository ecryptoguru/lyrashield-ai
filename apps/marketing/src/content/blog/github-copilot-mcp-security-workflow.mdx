This workflow connects GitHub Copilot CLI to LyraShield through the pinned MCP adapter. Authenticate separately with CLI OAuth, merge the client configuration, confirm discovery and make a read-only workspace call before using the tools. Plugin installation remains gated on a reviewed matching immutable Agent Plugin release. Copilot CLI has no documented LyraShield skills installation path, so use its supported direct-MCP setup. The [Copilot integration guide](/docs/integrations/github-copilot) owns current setup; the [vibe coding security guide](/blog/vibe-coding-security-guide) provides broader review context.

## 1. Authenticate local stdio

Use Node.js 24 or newer and run `npx -y lyrashield@0.2.14 login --oauth` in the same OS account that starts Copilot CLI. Select one authorized workspace in the browser. The local adapter reads the CLI credential store, so no credential belongs in committed MCP configuration. A teammate must complete their own login and workspace selection; sharing the project entry does not share authentication. Keep the credentials file private, and repeat consent when access expires or is revoked.

The [Node.js downloads page](https://nodejs.org/en/download) describes the runtime. A missing Node executable and a denied workspace read are different failures: first confirm the client can start `npx`, then inspect the authenticated service response. Use `npx -y lyrashield@0.2.14 doctor` to inspect local setup, while keeping client discovery and an authenticated tool call as separate checks. Doctor cannot prove a skill was loaded, a scan was accepted or a hosted write is authorized.

## 2. Plugin release boundary

The marketplace default branch contains preparation artifacts. Do not register that branch or enable its plugin in shared repository settings. Plugin installation needs a reviewed matching immutable package release. The earlier CLI 0.2.13 release printed obsolete marketplace instructions; do not infer a supported plugin route from that older output. The pinned CLI provides a safe config writer for the Copilot CLI contract; preview it with `npx -y lyrashield@0.2.14 install copilot-cli --dry-run` before applying. Do not copy candidate plugin files from the preparation repository; plugin installation remains gated on a reviewed matching release.

Copilot CLI, Copilot in VS Code and Copilot Cloud Agent are distinct surfaces. For VS Code, follow the [VS Code MCP guide](/docs/integrations/vscode), which uses `servers` and a per-entry stdio type. The [Copilot Cloud Agent guide](/docs/integrations/github-copilot-cloud-agent) uses a private read-only Agents secret and a narrow tool allowlist; it cannot authenticate through the portable plugin's OAuth descriptor. Do not share a local credential store with that cloud environment or substitute an Actions secret for an Agents secret. A client capability listed in documentation does not mean an unpublished LyraShield bundle is available.

## 3. Merge the pinned direct MCP configuration

The [Copilot CLI configuration guide](/docs/integrations/copilot-cli) documents global `~/.copilot/mcp-config.json` and project `.mcp.json` or `.github/mcp.json` scope. Preserve existing server definitions when adding this entry. For a personal setup, use the global file; project entries also require the client's project trust checks. The stdio connection uses the coordinated pinned package version:

```json
{
  "mcpServers": {
    "lyrashield": {
      "type": "local",
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp@0.2.12"]
    }
  }
}
```

Do not add a raw key or token to this block. For a narrow initial read-only setup, select only the workspace, target, advisory diff and readiness tools your review needs. Recheck the allowlist when changing the server version instead of enabling every tool by default. The [official Copilot MCP documentation](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers) explains server management and allowlists. The [MCP transport documentation](https://modelcontextprotocol.io/docs/getting-started/intro) explains local process and remote transport boundaries. A local adapter still contacts the hosted LyraShield service; stdio does not mean scans or account data remain entirely on the machine.

## 4. Confirm discovery and authenticated access

Restart Copilot CLI, then enter `/mcp show lyrashield` in its interactive session. Inspect the server status and tools before asking for a service call. Next, ask Copilot to call `lyrashield_list_workspaces` and confirm the intended workspace, then list its authorized targets. A successful read proves that access at that moment, while an installed badge or listed server proves only discovery. Keep error and incomplete states visible rather than describing a failed check as a clean security result.

Request recorded scans explicitly for an authorized target and review the returned execution and evidence states. Advisory diff checks do not create a retained scan record. Findings require triage; they do not automatically prove exploitability or independent verification. An authenticated read does not establish scan, write, revocation or upgrade acceptance. For the separate remote route, follow the canonical guide's authentication contract. A hosted API key grants read access only and cannot replace a browser-confirmed OAuth delegation for scans, fix proposals or retests. CLI OAuth authenticates local stdio separately.

For a failed scan or interrupted request, keep the returned scan or operation identifier and inspect its recorded state before retrying. An unfinished request is not a successful review, and a repeated prompt must not silently create duplicate paid work.

## 5. Add the GitHub Action diff gate

Wire the workflow into CI so every pull request is scanned on the changed diff, not the whole repository. The LyraShield GitHub Action runs on pull request events, targets the changed files and emits SARIF output you can ingest. Approval gated fix proposals are proposals requiring review, so the action blocks only on new findings while a human approves any fix. The [GitHub Actions security hardening guide](https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions) describes the permissions and secret handling to apply. Run the action on every pull request so review cannot be skipped under deadline pressure and pin your action versions so an upstream change cannot alter your gate. Store any token the action needs as a GitHub Actions secret rather than in the workflow file and give the job the minimum permissions it needs, because a scanner job does not need write access to your repository contents. The action uploads the SARIF file to the GitHub security tab via the CodeQL upload action, so findings appear alongside existing code scanning alerts and each finding links back to the changed file in the pull request diff. Because the scan targets only the changed files in the diff range, the action runs fast even on large repositories where a full scan would timeout.

```yaml
name: LyraShield Security Check
on:
  pull_request:
    types: [opened, synchronize, reopened]
permissions:
  contents: read
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: ecryptoguru/lyrashield-ai@v2
        with:
          fail_on_severity: HIGH
```

## 6. Add an agent rules snippet

Review or extend `.github/copilot-instructions.md` manually, preserving existing guidance. Keep your project rules focused on how the team should use the workflow. A short snippet tells Copilot to run a check before completing a feature and to attach evidence to the pull request. Keep the snippet under ten lines so Copilot treats it as a standing rule and phrase each rule as an imperative so the agent treats it as non negotiable. If your team has a severity threshold, name it in the snippet.

```markdown
Before finishing a feature, run a LyraShield security check and attach the findings link to the pull request. Never commit secrets. If a high severity issue is found, stop and ask for review.
```
