You can review AI generated pull requests in Codex with evidence-state AppSec findings by connecting LyraShield AI through MCP, running a targeted scan from your Codex session, and enforcing the same policy in CI with a diff aware gate. The config lives in `~/.codex/config.toml` and supports both local stdio and remote HTTP with a bearer token.

OpenAI Codex excels at large refactors, but refactors can introduce auth bypasses, injection, and vulnerable dependencies that are hard to spot in a diff. The [vibe coding security guide](/blog/vibe-coding-security-guide) describes why AI built code needs findings with recorded evidence states instead of noisy lint. LyraShield AI is agent native AppSec for AI built software that follows Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report. This guide gives you the exact `~/.codex/config.toml` entries for local and remote MCP using `npx -y @lyrashield/mcp` and `https://app.lyrashieldai.com/api/mcp`, plus verification, inline checks, and a GitHub Action. Findings retain their recorded evidence states; independent verification requires a separate receipt. Current LyraShield tools record fix proposals and queue retests but do not edit code, create branches, or open pull requests.

## 1. Prerequisites and setup

You need Codex CLI 0.12 or newer, Node 18 or newer, a LyraShield key starting with `lsk_`, and a repo where you can add GitHub workflows. Codex loads MCP from `~/.codex/config.toml`, as described in the [Codex MCP docs](https://github.com/openai/codex) under MCP servers. Keep your key in env, not in files. Register the configured server, then use `codex mcp list` to confirm tool discovery. Review baseline risks through [OWASP Top 10](https://owasp.org/www-project-top-ten/) and weak config guidance from [CISA secure by design](https://www.cisa.gov/securebydesign). For dependency risk, browse [OSV](https://osv.dev/) to see how advisories map to versions. The [Model Context Protocol spec](https://modelcontextprotocol.io/docs/getting-started/intro) explains how tools like `scan` and `list_findings` are exposed. Every Codex session reads `~/.codex/config.toml` on startup, so one edit registers MCP tools for all projects. Confirm `codex --version` shows 0.12 or higher and `node --version` shows 18 or higher, since older builds ignore `bearer_token_env_var`. Store `LYRASHIELD_API_KEY` in your shell profile or a secret manager, never inside the repo.

## 2. Configure Codex MCP servers

Edit `~/.codex/config.toml` to register LyraShield. The canonical pattern is in the [OpenAI Codex integration guide](/docs/integrations/openai-codex). Do not write bare internal paths in your own docs, link them as [OpenAI Codex integration guide](/docs/integrations/openai-codex).

Local stdio example:

```toml
[mcp_servers.lyrashield]
command = "npx"
args = ["-y", "@lyrashield/mcp"]
env = { LYRASHIELD_API_KEY = "${LYRASHIELD_API_KEY}" }
startup_timeout_sec = 20
tool_timeout_sec = 120
```

Remote HTTP with Bearer:

```toml
[mcp_servers.lyrashield_remote]
command = "npx"
args = ["-y", "@lyrashield/mcp", "--remote", "--url", "https://app.lyrashieldai.com/api/mcp"]
bearer_token_env_var = "LYRASHIELD_API_KEY"
env = { LYRASHIELD_MCP_URL = "https://app.lyrashieldai.com/api/mcp" }
startup_timeout_sec = 20
tool_timeout_sec = 120
```

Remote URL is [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp) with `Authorization: Bearer lsk_...` derived from the token env var. The config uses the pinned npx form and exposes env expansion through `bearer_token_env_var` which Codex resolves at runtime. If you are comparing editor flows, the related [Codex security workflow](/blog/codex-security-workflow) checklist shows a similar gate pattern, and sibling editors are covered in guides like the [Cline AI app security checklist](/blog/cline-app-security-checklist) for team wide rollout.

The local stdio entry is best for solo dev because Codex spawns the MCP server as a child process with no network hop, keeping latency low. The remote HTTP entry suits team keys and CI because `bearer_token_env_var` lets you rotate the secret in one place. Each `[mcp_servers.*]` block needs `command` to launch `npx`, `args` to pin `@lyrashield/mcp`, and either `env` for stdio or `bearer_token_env_var` for remote auth. Keep `startup_timeout_sec` at 20 so cold starts of `npx` do not trip the watchdog, and raise `tool_timeout_sec` to 120 for large repos.

## 3. Verify the connection in Codex

Start a new Codex session with `codex --verbose` and run `codex mcp list` or ask the agent "list MCP servers". You should see `lyrashield` and `lyrashield_remote` as available. Try a dry tool call: "call lyrashield_get_scan_status". If it fails, check that `LYRASHIELD_API_KEY` is exported and that Node can resolve `npx`. Common failure is launching Codex from a GUI that does not inherit shell env. For auth debugging, the [OpenAI platform docs](https://openai.com/index/openai-api/) discuss bearer handling, and [docs.github.com on encrypted secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions) covers secret propagation for CI parity. Reopen Codex after package upgrades so `npx` resolves the current package. If `bearer_token_env_var` is set but the env var is empty, Codex connects without auth and the server rejects calls with a 401, which shows as a tool error rather than a crash.

## 4. Run an inline scan from a Codex session

In your Codex prompt, target the authorized workspace and request a focused scan. Ask for every finding’s recorded evidence state, supporting evidence, file location, CWE, and limitations. Call `lyrashield_scan_target`, then use `lyrashield_get_findings`; do not request “verified findings only,” because detection and independent verification are separate states.

A finding retains its recorded evidence state, supporting detail, file location, CWE, severity, and limitations when available. Evidence strength and reproducibility depend on that state; detection alone does not imply a reachable sink, confirmed vulnerable call path, or independent verification. When you ask the agent to show findings, request the evidence block so the PR reviewer can assess the same recorded context without rerunning the scan. Independent verification still requires a separate receipt.

Example Codex instruction you can paste:

```md
Use lyrashield MCP to scan this repo diff against main.

- Return findings with their recorded evidence states, supporting evidence, and fix guidance.
- Group by risk: auth, injection, secrets, supply chain
- Record the intended remediation with `lyrashield_record_fix_proposal`; do not claim that LyraShield generated or applied a patch.
```

`lyrashield_record_fix_proposal` stores a remediation summary; it does not produce a patch. After a developer changes the code, `lyrashield_verify_fix` queues a retest and returns a scan reference to poll.

## 5. Wire the GitHub Action diff aware gate

Add `.github/workflows/lyrashield.yml` to enforce the same policy on pull requests. This keeps Codex refactor safety aligned with CI and surfaces SARIF in code scanning as described in [GitHub docs for SARIF upload](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github).

```yaml
name: lyrashield diff gate
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - uses: ecryptoguru/lyrashield-ai@v1
        with:
          fail_on_severity: HIGH
```

The `--diff` flag limits analysis to changed files, which is critical for Codex generated PRs that touch many files. SARIF upload lets you use GitHub code scanning rules to block merges on critical findings with recorded evidence states while still keeping low risk notes informational. The diff aware gate matters because a full repo scan on a large codebase can time out the job and drown reviewers in preexisting issues, whereas the diff scan returns only findings tied to the PR changes. Add a branch protection rule requiring the gate to pass before merge.

## 6. Add agent rules snippet for Codex

Create `.codex/rules/security.md` so every Codex agent run follows the same loop.

```md
# Security loop for Codex

- Identify Target: app root, entry routes, data classification.
- Scan via LyraShield MCP before final answer on refactors.
- Summarize findings with recorded evidence states only, with evidence path and CWE.
- Record a fix proposal, apply the code change outside LyraShield, then queue and poll a retest.
- Append Report section: scan ID, SARIF file, policy version.
```

This rule file codifies Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report. It tells Codex to preserve evidence states, use `lyrashield_record_fix_proposal` only for the remediation record, and use `lyrashield_verify_fix` only to queue a retest after code changes are applied. Neither tool writes code or opens a branch or pull request.

| Step           | Codex action                     | LyraShield MCP tool                                   | Output                          |
| -------------- | -------------------------------- | ----------------------------------------------------- | ------------------------------- |
| Target         | Identify app root and risk areas | lyrashield_list_targets                               | target inventory                |
| Scan           | Run scoped scan via MCP          | lyrashield_scan_target                                | SARIF + findings                |
| Verify         | Triage with evidence             | lyrashield_get_findings                               | findings + evidence states      |
| Fix and retest | Propose patch and rerun          | lyrashield_record_fix_proposal, lyrashield_verify_fix | proposal record + retest status |
| Report         | Summarize in PR body             | lyrashield_create_report                              | audit note                      |

## 7. Why pair Codex with LyraShield

Codex accelerates code change, LyraShield adds the verification layer that is designed to be evidence driven. The [vibe coding security guide](/blog/vibe-coding-security-guide) explains how fast scaffolding without verification leaves injection and auth gaps that show up late. By pairing, you get a single loop in both editor and CI, plus SARIF that integrates with existing GitHub policy. LyraShield v1 covers agentic pentest plus SCA plus secrets plus GitHub Action plus SARIF, so you can replace ad hoc scripts with one consistent flow. Sprints 0 to 2 are shipped, while scan engine MVP, automatic branch and pull-request execution, and billing are on the roadmap and described as designed to capabilities. The pairing works because Codex owns the change and LyraShield owns the evidence, so the same finding with a recorded evidence state flows from editor to CI without reformatting. When a Codex refactor touches auth middleware, the diff scan catches bypasses that unit tests miss.
