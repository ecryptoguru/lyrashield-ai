You can review AI generated pull requests in Codex with verified AppSec evidence by connecting LyraShield AI through MCP, running a targeted scan from your Codex session, and enforcing the same policy in CI with a diff aware gate. The config lives in `~/.codex/config.toml` and supports both local stdio and remote HTTP with a bearer token.

OpenAI Codex excels at large refactors, but refactors can introduce auth bypasses, injection, and vulnerable dependencies that are hard to spot in a diff. The [vibe coding security guide](/blog/vibe-coding-security-guide) describes why AI built code needs verified findings instead of noisy lint. LyraShield AI is agent native AppSec for AI built software that follows Target to Scan to Verified Finding to Fix PR to Retest to Report. This guide gives you the exact `~/.codex/config.toml` entries for local and remote MCP using `npx -y @lyrashield/mcp` and `https://app.lyrashieldai.com/api/mcp`, plus verification, inline checks, and a GitHub Action.

## 1. Prerequisites and setup

You need Codex CLI 0.12 or newer, Node 18 or newer, a LyraShield key starting with `lsk_`, and a repo where you can add GitHub workflows. Codex loads MCP from `~/.codex/config.toml`, as described in the [Codex MCP docs](https://github.com/openai/codex) under MCP servers. Keep your key in env, not in files. Register the configured server, then use `codex mcp list` to confirm tool discovery. Review baseline risks through [OWASP Top 10](https://owasp.org/www-project-top-ten/) and weak config guidance from [CISA secure by design](https://www.cisa.gov/securebydesign). For dependency risk, browse [OSV](https://osv.dev/) to see how advisories map to versions. The [Model Context Protocol spec](https://modelcontextprotocol.io/docs/getting-started/intro) explains how tools like `scan` and `list_findings` are exposed. Every Codex session reads `~/.codex/config.toml` on startup, so one edit registers MCP tools for all projects. Confirm `codex --version` shows 0.12 or higher and `node --version` shows 18 or higher, since older builds ignore `bearer_token_env_var`. Store `LYRASHIELD_API_KEY` in your shell profile or a secret manager, never inside the repo.

## 2. Configure Codex MCP servers

Edit `~/.codex/config.toml` to register LyraShield. The canonical pattern is in the [OpenAI Codex integration guide](/docs/integrations/openai-codex). Do not write bare internal paths in your own docs, link them as [OpenAI Codex integration guide](/docs/integrations/openai-codex).

Local stdio example:

```toml
[mcp_servers.lyrashield]
command = "npx"
args = ["-y", "@lyrashield/mcp"]
env = { LYRASHIELD_API_KEY = "${LYRASHIELD_API_KEY}" }
startup_timeout_sec = 20
tool_timeout_sec = 120
```

Remote HTTP with Bearer:

```toml
[mcp_servers.lyrashield_remote]
command = "npx"
args = ["-y", "@lyrashield/mcp", "--remote", "--url", "https://app.lyrashieldai.com/api/mcp"]
bearer_token_env_var = "LYRASHIELD_API_KEY"
env = { LYRASHIELD_MCP_URL = "https://app.lyrashieldai.com/api/mcp" }
startup_timeout_sec = 20
tool_timeout_sec = 120
```

Remote URL is [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp) with `Authorization: Bearer lsk_...` derived from the token env var. The config uses the pinned npx form and exposes env expansion through `bearer_token_env_var` which Codex resolves at runtime. If you are comparing editor flows, the related [Codex security workflow](/blog/codex-security-workflow) checklist shows a similar gate pattern, and sibling editors are covered in guides like the [Cline AI app security checklist](/blog/cline-app-security-checklist) for team wide rollout.

The local stdio entry is best for solo dev because Codex spawns the MCP server as a child process with no network hop, keeping latency low. The remote HTTP entry suits team keys and CI because `bearer_token_env_var` lets you rotate the secret in one place. Each `[mcp_servers.*]` block needs `command` to launch `npx`, `args` to pin `@lyrashield/mcp`, and either `env` for stdio or `bearer_token_env_var` for remote auth. Keep `startup_timeout_sec` at 20 so cold starts of `npx` do not trip the watchdog, and raise `tool_timeout_sec` to 120 for large repos.

## 3. Verify the connection in Codex

Start a new Codex session with `codex --verbose` and run `codex mcp list` or ask the agent "list MCP servers". You should see `lyrashield` and `lyrashield_remote` as available. Try a dry tool call: "call lyrashield.scan_status". If it fails, check that `LYRASHIELD_API_KEY` is exported and that Node can resolve `npx`. Common failure is launching Codex from a GUI that does not inherit shell env. For auth debugging, the [OpenAI platform docs](https://openai.com/index/openai-api/) discuss bearer handling, and [docs.github.com on encrypted secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions) covers secret propagation for CI parity. Reopen Codex after package upgrades so `npx` resolves the current package. If `bearer_token_env_var` is set but the env var is empty, Codex connects without auth and the server rejects calls with a 401, which shows as a tool error rather than a crash.

## 4. Run an inline scan from a Codex session

In your Codex prompt, target the workspace and request a focused scan: "scan the current repo for XSS, auth, and secrets, show only verified findings with file and line". LyraShield is designed to filter to verified findings with evidence and is designed to support retest after a Fix PR, both capabilities are on the roadmap and not claimed as live automatic behavior today. Map findings to [CWE Top 25](https://cwe.mitre.org/top25/archive/2024/2024_cwe_top25.html) for consistent naming and to [NIST SSDF](https://csrc.nist.gov/Projects/ssdf) practices for secure development hygiene. For dependency findings, attach an [OSV](https://osv.dev/) link in the PR body so reviewers can validate version ranges.

A verified finding is not a raw heuristic. It includes a file, a line range, and proof, such as a reachable sink or a confirmed vulnerable call path, plus the CWE and severity. A raw heuristic might flag any use of `eval` as dangerous, but LyraShield is designed to keep only findings where the tainted input path is reproducible, so your Codex review stays focused on real risk instead of triaging noise. When you ask the agent to show findings, request the evidence block so the PR reviewer can follow the same path without re running the scan.

Example Codex instruction you can paste:

```md
Use lyrashield MCP to scan this repo diff against main.
- Return only verified findings with evidence and fix guidance
- Group by risk: auth, injection, secrets, supply chain
- Propose a Fix PR diff for each critical, do not apply without confirmation
```

The Fix PR step is designed to produce a minimal patch plus tests and is on the roadmap. Keep report steps explicit so audit trails include scan ID and SARIF artifact links.

## 5. Wire the GitHub Action diff aware gate

Add `.github/workflows/lyrashield.yml` to enforce the same policy on pull requests. This keeps Codex refactor safety aligned with CI and surfaces SARIF in code scanning as described in [GitHub docs for SARIF upload](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github).

```yaml
name: lyrashield diff gate
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - uses: ecryptoguru/lyrashield-ai@v1
        with:
          fail_on_severity: HIGH
```

The `--diff` flag limits analysis to changed files, which is critical for Codex generated PRs that touch many files. SARIF upload lets you use GitHub code scanning rules to block merges on critical verified findings while still keeping low risk notes informational. The diff aware gate matters because a full repo scan on a large codebase can time out the job and drown reviewers in preexisting issues, whereas the diff scan returns only findings tied to the PR changes. Add a branch protection rule requiring the gate to pass before merge.

## 6. Add agent rules snippet for Codex

Create `.codex/rules/security.md` so every Codex agent run follows the same loop.

```md
# Security loop for Codex

- Identify Target: app root, entry routes, data classification.
- Scan via LyraShield MCP before final answer on refactors.
- Summarize verified findings only, with evidence path and CWE.
- Propose Fix PR with minimal diff and tests, then request retest.
- Append Report section: scan ID, SARIF file, policy version.
```

This rule file codifies Target to Scan to Verified Finding to Fix PR to Retest to Report and avoids language that implies fixes land unattended. For broader editor coverage, link your team to the [OpenAI Codex integration guide](/docs/integrations/openai-codex) and the pillar [vibe coding security guide](/blog/vibe-coding-security-guide) inside the first third of your internal docs, which keeps onboarding aligned. Treat the rules file as approval gated fix proposals, not unattended fixes, so every patch lands only after a human reviews the diff and the retest result. The snippet also keeps Codex from summarizing unverified hints as if they were confirmed.

| Step | Codex action | LyraShield MCP tool | Output |
| --- | --- | --- | --- |
| Target | Identify app root and risk areas | list_targets | target inventory |
| Scan | Run diff scan via MCP | scan --diff | SARIF + findings |

| Fix and retest | Propose patch and rerun | create_fix_pr, retest | Fix PR + new SARIF |

When a Codex refactor touches auth middleware, the diff scan catches bypasses that unit tests miss.
