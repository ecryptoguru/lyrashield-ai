To connect Devin CLI to LyraShield, run npx lyrashield install devin so the CLI writes the MCP server entry to .devin/config.local.json, then run npx lyrashield doctor to verify the connection and credentials. Devin CLI is the Cognition command line agent, separate from Devin Desktop and Windsurf, and only stdio transport is documented for its MCP servers. This workflow covers the install, manual fallback, verification, an inline check, a CI gate, and a rules snippet.

The [vibe coding security guide](/blog/vibe-coding-security-guide) separates generated code from the controls that enforce what it may do. Wiring LyraShield into Devin CLI puts release assurance inside the terminal session, so a scan runs before a change reaches a pull request rather than only after. The steps below assume you have Node installed and an active LyraShield account.

| Step | Command or file | Purpose |
| --- | --- | --- |
| Prerequisites | Node 20 plus, git, LyraShield account | Prepare the environment |
| Install | npx lyrashield install devin | Write the MCP server entry |
| Manual path | .devin/config.local.json | Fallback if CLI is unavailable |
| Verify | npx lyrashield doctor | Check config and credentials |
| Inline check | npx lyrashield scan | Run a scan from the session |
| CI gate | .github/workflows/lyrashield.yml | Diff aware gate on pull requests |

## 1. Meet the prerequisites

Install Node 20 or later, which the [Node.js release guide](https://nodejs.org/en/docs/) covers. Confirm git is configured for your repository. Create a LyraShield account at [lyrashieldai.com](https://lyrashieldai.com) if you do not have one, because the MCP server needs credentials to authenticate. Run npx lyrashield login to store your credentials in ~/.lyrashield/credentials.json, which is not committed to version control.

Devin CLI manages MCP servers with the devin mcp commands: add to register a server, login to authenticate, enable to turn a server on, and disable to turn it off. Connected tools are namespaced as mcp__name, so you can see which server a tool call came from. Keep your credentials file outside the working tree, and never paste a token directly into a config file the agent can read.

## 2. Add the LyraShield MCP server

Run npx lyrashield install devin. The CLI writes the server entry to .devin/config.local.json with a root mcpServers key, and the file is gitignored by default. The canonical wiring is in the [Devin CLI integration guide](/docs/integrations/devin-cli). Only stdio transport is documented for CLI MCP servers. The [Model Context Protocol specification](https://modelcontextprotocol.io/) defines the transport and tool exposure contract.

If the CLI is unavailable, add the entry manually. This is the manual path, and it is exactly what the CLI writes:

```
{
  "mcpServers": {
    "lyrashield": {
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp", "stdio"],
      "env": { "LYRASHIELD_API_KEY": "lsk_YOUR_KEY" }
    }
  }
}
```

The gitignore default protects local credentials but also means the team does not share the same server set automatically. If you need a shared definition, store the server entries in a separate committed file that references environment variables instead of literal secrets. Use the devin mcp enable and devin mcp disable commands to control which servers are active in a session.

## 3. Verify the connection

Run npx lyrashield doctor. It checks that .devin/config.local.json is valid, the server entry is present, and your credentials resolve. If any check fails, the doctor reports the gap and the fix, so you can correct it before running a scan. A green doctor result means Devin CLI can reach the LyraShield server and authenticate.

Restart your Devin CLI session after editing the config file so the agent loads the new server entry. Confirm the LyraShield tools appear under the mcp__lyrashield namespace. If the tools are missing, check the command and args spelling, the token, and whether the server is enabled. The doctor does not run a scan; it only confirms the wiring. If a check fails, the doctor names the file, the field, and the expected value, so you can fix the gap without reading the full config. Run the doctor again after each fix until every check is green, because a partial fix can leave the server reachable but unable to authenticate.

## 4. Run an inline security check

With the connection verified, run npx lyrashield scan from your project root. The scan targets the repository, reviews the code for candidate issues, and records evidence in an immutable assurance record. Detected issues stay in a detected state until independent verification confirms the behavior, so a finding is a prompt to investigate, not a verdict. Read each finding in the session, note the file and line, and decide whether the candidate reflects a real weakness or a false positive that deserves a recorded dismissal. The assurance record holds both the confirmed issues and the dismissed ones, so a reviewer can see the full set of decisions, not just the open items.

Review the scan output in the session. If a candidate issue is real, a fix proposal is generated for review. Approval gated fix proposals require a human review before a patch reaches a pull request, so a fix is never automatic. ## 5. Gate pull requests with the GitHub Action

Add the LyraShield GitHub Action to your CI so every pull request is scanned. The action runs a diff aware gate, which means only changed code is scanned on each pull request, keeping the check fast enough to run on every push. Output is SARIF, which GitHub renders in the security tab. The [GitHub Actions documentation](https://docs.github.com/en/actions) covers workflow syntax and the [GitHub SARIF integration](https://docs.github.com/en/code-security) explains how findings appear. Store the LyraShield token as a repository secret rather than a variable, so it stays encrypted and masked in logs. Set the diff aware flag to true so the action scans only the lines a pull request changes, which keeps the gate fast on large repositories and avoids re-scanning untouched code on every run.

Add a workflow file named lyrashield.yml under the .github/workflows directory:

```
name: LyraShield
on:
  pull_request:
    branches: [main]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: lyrashield/scan-action@v1
        with:
          diff-aware: true
          sarif: true
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: lyrashield.sarif
```

## 6. Add a rules snippet to AGENTS.md

Tell Devin CLI to use LyraShield before proposing a fix. Add a line to AGENTS.md in your project root:

```
Run the LyraShield scan tool before proposing a fix. Do not apply a patch until a human reviews the fix proposal. Keep detected issues in a detected state until independent verification confirms the behavior.
```

A rules file states intent. The approval gate enforces it. A prompt can be changed in a pull request or ignored under pressure, but a server side gate that blocks a patch until a human binds it to an approval cannot be talked past. That is the difference between stating a policy and holding one. Require a security owner for changes to agent configuration, and include AGENTS.md in normal code review and branch protection.
