This workflow sets up the LyraShield MCP security workflow for Kiro so the agent can run security checks inside your project. It leads with the Agent Plugin one step install and the LyraShield CLI, then covers the manual path, verification, an inline check, a GitHub Action diff gate, and an agent rules snippet. Pair it with the [vibe coding security guide](/blog/vibe-coding-security-guide) for broader context.

## 1. Install prerequisites and authenticate

Install Node so the `npx` commands resolve, then run `npx lyrashield login` to store your credentials in a local file under your home directory. Nothing is committed to the repository, because credentials live in a per user file and the CLI never writes them into source. This matters for shared repos where a committed token would leak to every collaborator and to the git history. Confirm with `npx lyrashield doctor` that the server is reachable and the credentials resolve before you touch Kiro, because a failed login surfaces here instead of mid install. The [Node.js downloads page](https://nodejs.org/en/download) is the canonical source for the runtime. Run login and doctor from the project root so any project scoped config is detected correctly, and re-run doctor whenever you suspect the connection has drifted. If you share a machine with teammates, note that the credentials file is per user, so each person runs login once rather than sharing a single credential file.

## 2. Install the Kiro Agent Plugin

For Kiro, the preferred path is the Agent Plugin one step install, which bundles the MCP server and a security skill into the Kiro plugins directory. The plugin lands in a per user plugins directory with a manifest file, an MCP server running over stdio, a security skill, and an AGENTS.md file that tells Kiro how to use the workflow. Run `npx lyrashield login` first so the plugin can resolve your credentials, then trigger the install so the manifest points at the right transport. The [Agent Plugins specification](https://agent-plugins.org/) defines the manifest format and how launch clients discover plugins. This is the primary path for Kiro because it is one step and keeps the server and skill versioned together, which means an update to the server ships with the matching skill rather than drifting apart. Keep the plugin directory under your home folder and out of version control, because committing it would share your local transport and token references with every collaborator. After install, open the plugin manifest once to confirm the server entry and the security skill are both present, since a partial install can leave the server reachable but the skill missing. If your team standardizes on the plugin, document the install command in your onboarding so every new contributor gets the same one step setup rather than a manual path. When Kiro loads the plugin, it reads the manifest to register the MCP server, then scans the security skill to decide when to invoke it, so a mismatch between the manifest transport and the installed skill causes the agent to silently skip checks.

## 3. Configure the manual path if needed

If you cannot use the plugin, the manual path is what the CLI writes when it configures Kiro. It runs the MCP server over stdio with `npx -y @lyrashield/mcp stdio`, or points at the remote endpoint `https://app.lyrashieldai.com/api/mcp` with a Bearer token prefixed `lsk_`. Add the server to the Kiro MCP configuration so the agent can reach it, and store the token in the local credentials file rather than the config you commit. The manual path is secondary because it does not bundle the security skill and AGENTS.md that the plugin provides, so you have to convey conventions yourself. The [Model Context Protocol transport documentation](https://modelcontextprotocol.io/) explains the stdio and remote transport options. Use the remote path when you cannot run a local Node process, and the stdio path when you want everything on your machine. Whichever you pick, store the Bearer token in the local credentials file that `npx lyrashield login` writes, and reference it from the config rather than pasting it inline, so a config file shared for troubleshooting never carries a live token. If you use the remote endpoint, rotate the Bearer token on a schedule, because a remote MCP server trusts the token alone for identity. Kiro design.md and spec.md hooks can reference the workflow by name, so when a hook fires the agent knows to call the registered server rather than requiring an inline reminder each time.

## 4. Verify the connection and run an inline check

After install, verify that Kiro can reach the server by asking the agent to run a security check on the current project. The agent should call the LyraShield tools to target the app, run review, and return findings you can act on. Confirm with `npx lyrashield doctor` that the plugin manifest is valid and the server is reachable, so you know setup succeeded without a manual guess. Run an inline check on a small change before wiring CI, because a green local run proves the credentials and transport are correct end to end. If the agent cannot see the tools, recheck the plugin directory and the credentials file, and confirm the plugin manifest names the right transport. A failed inline check is cheaper to debug now than a red CI run later. If the inline check returns findings, read them before wiring CI so you understand the output format the GitHub Action will produce, and so you can set expectations with your team about what a blocked build looks like. Each finding links back to an immutable assurance record, so you can paste that link into a pull request comment as evidence the check ran and what it found, which gives reviewers something concrete to approve rather than a bare pass or fail status.

## 5. Add the GitHub Action diff gate

Wire the workflow into CI so every pull request is scanned on the changed diff, not the whole repository. The LyraShield GitHub Action runs on pull request events, targets the changed files, and emits SARIF output you can ingest. Approval gated fix proposals are proposals requiring review, so the action blocks only on new findings while a human approves any fix. The [GitHub Actions security hardening guide](https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions) describes the permissions and secret handling to apply. Run the action on every pull request so review cannot be skipped under deadline pressure, and pin your action versions so an upstream change cannot alter your gate. Store any token the action needs as a GitHub Actions secret rather than in the workflow file, and give the job the minimum permissions it needs, because a scanner job does not need write access to your repository contents. The scan command uses `--diff` with the base and head SHAs, so it only analyzes files touched by the pull request, which keeps the gate fast and focused on new risk rather than re flagging pre existing issues. The SARIF upload surfaces findings in the Security tab, so reviewers see them in the same place as other code scanning results without switching tools.

```yaml
name: LyraShield Security Check
on:
  pull_request:
    types: [opened, synchronize, reopened]
permissions:
  contents: read
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - run: npx -y @lyrashield/mcp scan --diff ${{ github.event.pull_request.base.sha }}..${{ github.event.pull_request.head.sha }} --format sarif > lyrashield.sarif
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: lyrashield.sarif
```

## 6. Add an agent rules snippet

Because the plugin ships an AGENTS.md file, keep your project rules focused on how the team should use the workflow. A short snippet tells Kiro to run a check before completing a feature and to attach evidence to the pull request.

```markdown
Before finishing a feature, run a LyraShield security check and attach the findings link to the pull request. Never commit secrets. If a high severity issue is found, stop and ask for review.
```

A rule like attach the findings link gives the agent a concrete artifact to produce, while a vague rule like be secure leaves it guessing at what evidence counts.
