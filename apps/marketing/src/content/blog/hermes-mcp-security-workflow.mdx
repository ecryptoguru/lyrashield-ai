You can pair Hermes AI with LyraShield AI over MCP to get target aware scans, verified findings, and fix PR drafts without leaving your agent workflow. In this guide you will add the local server using pinned npx -y @lyrashield/mcp plus the remote endpoint at https://app.lyrashieldai.com/api/mcp inside ~/.hermes/config.yaml, verify tool discovery, run a scoped inline check, and wire a diff aware GitHub Action gate that uploads SARIF for code scanning.

Fast generation from Hermes is powerful, but without verification you can ship injection flaws, broken access control, and vulnerable deps. Use the [vibe coding security guide](/blog/vibe-coding-security-guide) as your policy spine, then map categories to [OWASP Top 10](https://owasp.org/www-project-top-ten/) and [CWE Top 25](https://cwe.mitre.org/top25/archive/cwe/top25.html) for concrete weakness definitions that justify your triage order. The combination of vibe coding speed with verified scans is what keeps agents productive while still satisfying review requirements that security teams care about.

LyraShield follows a clear loop of Target to Scan to Verified Finding to Fix PR to Retest to Report, designed to keep human approval in place while the engine matures.

## 1. Prerequisites and project baseline

You need Node.js 20 or newer which you can confirm via [Node.js docs](https://nodejs.org/en/docs), Hermes installed locally, Git with PR workflow, and a LyraShield API key shaped as lsk_... Export LYRASHIELD_API_KEY in your shell and never commit the raw value. Hermes reads `${env:VAR}` inside config.yaml at startup, so the indirect reference stays safe.

LyraShield v1 is designed to cover agentic pentest plus SCA plus secrets scanning plus GitHub Action plus SARIF. Scan engine MVP and fix PR automation are on the roadmap and not yet live, so treat this as designed to require human review before merge. Read [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) to see why stdio suits local tools and streamable http suits remote servers.

Quick sanity check before editing config:

```bash
node -v
npm view @lyrashield/mcp version
ls ~/.hermes/
echo $LYRASHIELD_API_KEY | wc -c
```

Keep a sibling checklist handy such as [Hermes app security checklist](/blog/hermes-app-security-checklist) for fix patterns that match your generated stack. That checklist helps you translate a verified finding into a concrete remediation, such as tightening auth middleware or upgrading a transitive dependency.

Define your target naming early. LyraShield treats target as the unit of verification. Examples include staging hermes app, production api, or a preview deployment. A clear naming convention prevents confusion when you later add both local and remote servers and start sharing reports across the team.

## 2. Configure LyraShield MCP server in Hermes

Hermes stores MCP servers in ~/.hermes/config.yaml under mcp_servers. Each entry supports tools.include and tools.exclude filters, ssl_verify flag, and env interpolation. Configure both local stdio and remote bearer.

```yaml
mcp_servers:
  lyrashield:
    transport: stdio
    command: npx -y @lyrashield/mcp
    env:
      LYRASHIELD_API_KEY: ${env:LYRASHIELD_API_KEY}
    tools:
      include:
        - scan_target
        - get_finding
        - list_targets
        - get_report
        - create_fix_pr_draft
    ssl_verify: true
  lyrashield-remote:
    transport: streamable-http
    url: https://app.lyrashieldai.com/api/mcp
    headers:
      Authorization: Bearer ${env:LYRASHIELD_API_KEY}
    tools:
      include:
        - scan_target
        - get_finding
        - list_targets
    ssl_verify: true
```

This pins local to npx -y @lyrashield/mcp and remote to https://app.lyrashieldai.com/api/mcp with bearer header. The canonical copy lives in [Hermes integration guide](/docs/integrations/hermes). Use `${env:VAR}` rather than raw keys. Keep tools.include explicit so only verification tools are exposed to the Hermes agent. Explicit includes also reduce accidental exposure of auxiliary tools that you do not want the agent to call without review.

If you run Hermes inside a shared container, mount the config file from a secure volume and ensure LYRASHIELD_API_KEY is injected via secret manager rather than baked into the image. That keeps rotation simple and avoids leaking keys into image layers.

## 3. Verify connection and list security tools

Restart Hermes after editing ~/.hermes/config.yaml. Open the MCP panel and expect lyrashield and lyrashield-remote to show connected with transport type stdio and streamable-http. If either shows failed, confirm that Node can resolve npx and that the shell that launched Hermes has LYRASHIELD_API_KEY exported. Also check that yaml indentation is exactly two spaces under mcp_servers, since Hermes uses strict yaml parsing.

Ask Hermes to list tools:

```text
Prompt: List MCP servers and tools from ~/.hermes/config.yaml.
Show transport, url or command, and tool names for lyrashield entries.
```

Expected output:

```text
lyrashield (stdio via npx -y @lyrashield/mcp):
- scan_target(target, scope)
- get_finding(id)
- list_targets()
- create_fix_pr_draft(finding_id)
- get_report(target_id)

lyrashield-remote (streamable-http at https://app.lyrashieldai.com/api/mcp):
- scan_target, get_finding, list_targets
```

For context on supply chain findings, skim [OSV database](https://osv.dev/) and for CI gating see [GitHub Actions docs](https://docs.github.com/en/actions). These references explain how SARIF and dependency data flow together. Seeing identical core tools across both servers confirms that your auth works for both transports.

## 4. Run an inline security check from Hermes

With tools listed, run a focused verification without leaving Hermes. Keep scope tight to changed files for fast feedback. Tight scope also helps you stay within context limits when Hermes pulls file contents for evidence.

```text
Prompt for Hermes agent:
Use lyrashield scan_target for target staging-hermes-app.
Scope: src/app/api, src/lib. Exclude generated .next and node_modules.
Return only verified findings with CWE, evidence, file and line, severity.
Add OWASP mapping when present.
Persist report id for PR gate.
```

A good response contains finding id, severity, CWE, file and line, evidence snippet, and suggested patch location. LyraShield is designed to surface verified findings with evidence instead of speculative lints, so prioritize verified items. See [OWASP Top 10](https://owasp.org/www-project-top-ten/) and [CWE Top 25](https://cwe.mitre.org/top25/archive/cwe/top25.html) for definitions when triaging. When a finding maps to injection, the evidence snippet usually shows the unsanitized sink, which makes the fix obvious without additional hunting.

This inline step also surfaces secrets that were templated into fixtures. Since v1 includes secrets scanning alongside SCA, one scan can reveal both hardcoded creds and vulnerable packages. Rotate any exposed secret before merging the fix PR.

Do not claim fixes are automatic. Fix PR drafts are designed to open a branch for review, keeping human approval central while automation matures.

## 5. Wire a diff aware GitHub Action gate

Local checks are fast, but teams need PR enforcement that survives skipped local steps. Wire the official GitHub Action in diff aware mode and upload SARIF.

```yaml
name: lyrashield security gate
on:
  pull_request:
    paths:
      - 'src/**'
      - 'app/**'
      - 'packages/**'
  push:
    branches: [main]

jobs:
  security:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: LyraShield diff scan
        uses: lyrashieldai/action@v1
        with:
          api-key: ${{ secrets.LYRASHIELD_API_KEY }}
          diff-mode: true
          target: auto
          sarif-output: results.sarif
          fail-on: high
      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
```

Require the security job in branch protection. The pairing of MCP for local dev and the Action for CI reflects ideas from [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) around keeping context close to the agent while enforcing policy centrally. Details for reusable workflows live in [GitHub Actions docs](https://docs.github.com/en/actions). Once required, developers cannot merge when high severity verified findings remain, which is the simplest way to keep vibe coded changes trustworthy without relying on manual checklists that get skipped under deadline pressure.

## 6. Add agent rules for consistent secure coding

Add a repo local rules file that Hermes loads, for example hermes.md or .hermes/rules.md at project root. This file makes secure behavior the default.

```markdown
# Hermes security rules
- Before finishing a feature, call lyrashield scan_target on changed scope.
- Only surface verified findings with CWE and file evidence.
- For high severity verified findings, draft a fix branch via create_fix_pr_draft but require review before merge.
- On every PR, ensure lyrashield security gate passed and SARIF uploaded.
- Reference OWASP Top 10 and internal vibe coding security guide when drafting PR descriptions.
- Never log raw secrets. Use ${env:LYRASHIELD_API_KEY}.
```

This file encodes the loop of Target to Scan to Verified Finding to Fix PR to Retest to Report as daily practice. Keep it in version control so all Hermes sessions inherit the guardrail. Teammates who clone the repo get identical verification without extra setup steps.

| Stage | Hermes behavior | LyraShield verification | Evidence artifact |
| --- | --- | --- | --- |
| Generation | Generates APIs and UI from prompts via nousresearch patterns | N/A | Prompt trace |
| Inline check | Calls scan_target with tight scope plus include filters | Verified findings plus SCA plus secrets with file proof | Finding id plus CWE plus file path |
| PR gate | Pushes diff to GitHub | Diff aware scan plus SARIF plus fail on high | GitHub check green and code scanning annotations |
| Fix loop | Opens draft branch on request | Context aware patch drafts designed to include tests | Retest that marks finding closed |

## Why pair Hermes with LyraShield

Hermes gives you strong local capability and prompt control, but local generation still needs centralized policy. LyraShield adds verified evidence rather than noisy warnings, maps issues to [OWASP Top 10](https://owasp.org/www-project-top-ten/) and [CWE Top 25](https://cwe.mitre.org/top25/archive/cwe/top25.html), explains dependency risk with context from [OSV database](https://osv.dev/), and keeps the workflow inside MCP so you avoid switching to a separate UI. The v1 scope stays honest: agentic pentest plus SCA plus secrets plus GitHub Action plus SARIF, with broader automation on the roadmap but not presented as live today. For Hermes users that value local control, this pairing preserves local execution for stdio while still giving you remote reporting via bearer auth when you need shared visibility.
