GitHub Copilot suggests code inline and now acts as an agent, so a security checklist must review permissions, secrets, dependency safety, and verifiable evidence. This checklist gives concrete Copilot specific steps for each area and pairs the review with [LyraShield AI](https://lyrashieldai.com) for detection plus immutable proof. For cross tool context see the [vibe coding security guide](/blog/vibe-coding-security-guide).

## 1. Review Copilot permissions and instruction files

Copilot behavior is shaped by a repository level instructions file and by managed organization policy, so review both before trusting suggestions. Inspect the copilot instructions file in code review like any other source file, because it can steer the agent toward patterns that bypass your standards and a small edit there changes every suggestion that follows. Limit which repositories Copilot can index under your enterprise policy, and disable content collection where retention is a concern, since indexed code can surface in ways your team did not intend. Confirm that custom instructions do not instruct the agent to skip security checks or commit secrets, because an instruction that says "keep examples runnable" can lead to real looking credentials in config. The [GitHub Copilot security documentation](https://docs.github.com/en/copilot/managing-copilot/managing-copilot-as-an-individual-subscriber/managing-copilot-policies-as-an-individual-subscriber) describes the available controls. Treat instruction files as code, because a small prompt edit can change what the agent generates across the repo. Copilot can write a copilot instructions file at the repository root, so add that file to your review checklist the same way you review source, and diff it on every change so a quiet edit does not slip in. Under an enterprise plan, confirm which repositories Copilot is allowed to index, because overbroad indexing can expose repos you did not mean to connect. Copilot Chat data retention adds a second dimension, because chat transcripts may include pasted snippets that carry secrets or internal context you did not intend to persist. Check your plan specific retention policy in managed settings, and disable snippet collection where long term storage is a concern.

## 2. Audit secrets in Copilot suggestions

Copilot can suggest code that includes example keys, tokens, and connection strings, so scan every accepted suggestion for hardcoded secrets before commit. Move real values into environment variables or a managed secrets store, and verify that no credential lands in the instructions file or in generated config, since those files are easy to overlook in review. Run a dedicated secrets scanner on the pull request diff rather than relying on visual review, because secrets take many formats and a busy reviewer will skim past a key that looks like a placeholder. The [CWE entry on cleartext storage of sensitive information](https://cwe.mitre.org/data/definitions/312.html) explains why this class of flaw persists in generated code. Rotate any credential that was written to a file before you caught it, because disk exposure should be treated as a leak, and check git history if the secret was already pushed. Extend the scanner to cover the copilot instructions file and generated config, not just source code, because Copilot sometimes embeds connection strings in YAML that a source only scanner will skip.

## 3. Validate dependencies Copilot introduces

Copilot often imports packages as it scaffolds features, so review the dependency manifest for unexpected or risky additions on every pull request. Pin versions instead of floating ranges, because a floating range lets a new, unreviewed version enter your build without a code change. Check each new package against a vulnerability database before merge, and treat transitive dependencies with the same scrutiny as direct ones, since a safe looking direct package can pull in a vulnerable transitive one. Remove packages the generated code imports but never calls, because dead dependencies still expand your attack surface and slow installs. Prefer packages with active maintainers and clear license terms, and note any package that appears in only one of your projects. The [OSV database](https://osv.dev/) is a free, queryable source for known vulnerabilities across ecosystems. Re-scan after every dependency update, since a transitive package can introduce an advisory even when your direct list is unchanged. Keep a deny list of packages your team has reviewed and rejected, so a future Copilot suggestion does not reintroduce them under a slightly different name. When Copilot imports a package you have never used, spend a minute on the registry checking its publish history and maintainer count before accepting it. Go one step further with dependency verification by comparing the resolved package hash against the registry published checksum, because a typo squatted package can share a similar name but will not match the expected hash. Audit the lockfile on every pull request, since Copilot can edit the manifest without updating the lock, and an inconsistent lock lets the build resolve a different version than the diff shows.

## 4. Capture verifiable evidence per pull request

A checklist run is only useful if you can prove it happened and what it found, so record the scanner output, the dependency review, and the secret scan verdict for each pull request. Link that evidence to the commit it covers, and keep detection results separate from the proof that review occurred, because conflating them lets a failed scan be silently edited to look clean later. Use the free [AI app security checklist tool](/tools/ai-app-security-checklist) to standardize what each review records, so a teammate can reconstruct what was checked without reading your mind. Store evidence where it cannot be retroactively modified, because the value is auditability across many AI assisted changes over time. Link the evidence record in the pull request description so a reviewer can find it in one click. If you work across multiple repositories, standardize the evidence location so an auditor does not have to learn a new layout per repo, because consistency is what makes evidence usable at scale. Note who reviewed each finding and what they decided, so a later reader can trace a dismissed alert back to its reasoning. Make the evidence capture verifiable by writing each record to a storage target that supports immutable or append only writes, because a mutable file can be quietly overwritten. Capture a timestamp and the commit SHA in every evidence entry so the record is anchored to a specific point in history.

## 5. Gate merges on the checklist

Wire the checklist into your pull request flow so review cannot be skipped under deadline pressure. Block merge when secrets are found, when a dependency has an unpatched high severity advisory, or when the evidence record is missing. Run the LyraShield GitHub Action on the changed diff so only new risks block the build, not preexisting ones that would otherwise stall every pull request. Surface results in the pull request comment so reviewers see the verdict alongside the suggestion, and require an explicit human acknowledgement before a blocked finding is dismissed. This mirrors how teams apply CI gates generally, as described in the [GitHub Actions security hardening guide](https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions). Treat the gate as the last automated checkpoint before a human merges, not as a substitute for reading the diff. When a finding is dismissed, require the reviewer to record why in the evidence record, so the dismissal is auditable later rather than a silent override. Strengthen the gate by tiering the block conditions so a critical secret leak stops the build immediately while a medium severity advisory allows a tracked override with a remediation due date, because an all or nothing gate trains reviewers to dismiss everything just to ship.

| Checklist area | What to review | Gate action |
| --- | --- | --- |
| Permissions and instructions | Instruction file, enterprise indexing policy | Review like source code |
| Secrets handling | Suggested keys, tokens, connection strings | Block merge, rotate |
| Dependencies | New packages, pinned versions, advisories | Block on high severity |
| Evidence | Scan output linked to commit | Require before merge |
