Add one of the configurations below to Zed's `settings.json`. Restart Zed, confirm the server in Settings → AI → MCP Servers, then make a read-only tool call from the Agent Panel. `lyrashield doctor` checks local setup; it does not prove that Zed discovered or called a tool.

You can secure AI built apps in Zed by connecting LyraShield AI through the [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) and reviewing findings with recorded evidence states directly from the editor, then enforcing the same policy in CI with a diff aware GitHub Action gate. Zed reads servers from `settings.json` under `context_servers`, supporting local stdio and remote HTTP with browser OAuth or a separately configured API key.

Zed is fast and agent native, which makes it popular for vibe coding, but speed can leave security gaps when dependencies and routes are scaffolded by agents. The [vibe coding security guide](/blog/vibe-coding-security-guide) frames this problem as unverified generation at scale. LyraShield AI follows a loop of Target to Scan to Evidence State to Fix Proposal to Retest to Report. This post shows current Zed configuration forms and a verification path. Zed documents remote OAuth, but that is not a substitute for a real-client read receipt for your version and platform.

## 1. Prerequisites and setup

Use a current Zed release, Node 24 or newer for local stdio and a GitHub repo where you can add workflows. Zed reads MCP servers from `settings.json` under `context_servers`; the [official Zed MCP guide](https://zed.dev/docs/ai/mcp) documents the current flat local command and remote URL forms. Remote OAuth starts in Zed when no Authorization header is configured. Do not add a key merely to preview the setup. Restart Zed after changing settings and verify a read-only call before relying on inline findings.

## 2. Configure the MCP server in Zed

Zed supports local stdio and remote HTTP MCP servers. Add one of these blocks to your Zed `settings.json`. The full reference lives in the [Zed integration guide](/docs/integrations/zed). An older nested `command.path` entry should be migrated to Zed's current flat `command`, `args` and `env` fields after backing up the existing settings file.

Local stdio mode:

```json
{
  "context_servers": {
    "lyrashield": {
      "command": "npx",
      "args": ["-y", "@lyrashield/mcp@0.2.8"],
      "env": {}
    }
  }
}
```

Remote HTTP mode with browser OAuth:

```json
{
  "context_servers": {
    "lyrashield-remote": {
      "url": "https://app.lyrashieldai.com/api/mcp"
    }
  }
}
```

The remote URL is [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp). Zed handles the OAuth browser flow for this entry; an API-key `headers` form is available only if your team deliberately chooses it. Local stdio uses the published `@lyrashield/mcp@0.2.8` package and requires a valid local LyraShield credential before authenticated calls. See the [Zed AI app security checklist](/blog/zed-ai-app-security-checklist) for client-side permission review. The runner-local CI Action is a separate check and does not share hosted finding IDs by default.

## 3. Verify the connection in Zed

Restart Zed after editing `settings.json`, then open Settings → AI → MCP Servers and check for an active indicator. In the Agent Panel, call `lyrashield_list_targets` and confirm an actual response before starting an authorized scan. For remote OAuth, finish Zed's browser connection flow if prompted. For local stdio, check the local credential source if authentication fails. An API-key fallback has its own credential and rotation path.

Record the Zed version, operating system, selected workspace, server transport and the returned target ID in your acceptance note. A green server indicator proves discovery, while the read response proves that this client session reached the intended LyraShield workspace. Repeat this check after a Zed or MCP package upgrade.

## 4. Run an inline security check from the editor

With the server green, target your current project root and run a scan from the prompt. Ask Zed to summarize each finding with its recorded evidence state. Cross-check dependencies against [OSV](https://osv.dev/) and code patterns against [CWE Top 25](https://cwe.mitre.org/top25/archive/2024/2024_cwe_top25.html). `lyrashield_generate_fix_plan` is read-only, while `lyrashield_record_fix_proposal` records an approved remediation summary; neither edits code, creates a branch or opens a PR. Apply the change in your normal development workflow, queue `lyrashield_verify_fix` and poll the returned scan to a terminal state. Keep the loop as Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report. Call a result independently verified only when a separate verification receipt exists.

## 5. Wire the GitHub Action diff aware gate

Editor checks catch issues early, CI gates prevent drift on pull requests. Add `.github/workflows/lyrashield.yml` with a SARIF upload so results appear in GitHub code scanning. The [GitHub docs for SARIF upload](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github) describe the required `security-events: write` permission. The workflow below uses the same pinned `npx` and remote endpoint pattern and keeps secretsGitHub scanning broad.

```yaml
name: lyrashield diff gate
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: ecryptoguru/lyrashield-ai@v2
        with:
          fail_on_severity: HIGH
```

This runs only on changed files, which keeps the gate fast and focused. SARIF output integrates with GitHub code scanning. If you need SCA and secrets history, see [docs.github.com on dependency review](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-supply-chain-security) for supply chain context. The action derives the pull-request diff, so a one-line edit avoids a full scan. SARIF lands in the GitHub Security tab, where each rule maps to a file and line. The local MCP server and the runner-local CI gate are complementary checks, not the same remote scan.

## 6. Add agent rules snippet

Add a short rule file so every agent session in Zed follows the same security loop. Save as `.agent/rules/security.md` or the equivalent rules directory you use.

```md
# Security rules for Zed agents

- Always start with Target identification: root, env and data class.
- Run LyraShield scan via MCP before proposing large refactors.
- Treat only findings with evidence states as blocking. Include evidence in the PR description.
- For Fix Proposal, propose minimal diff, add tests for the finding with an evidence state and request retest.
- Update Report notes with scan ID and SARIF link.
```

This keeps behavior consistent between human and agent edits. The rule avoids phrases implying unattended fixes and frames the Fix Proposal as a proposed change designed to be reviewed. Think of the rules file as the contract your agent follows unsupervised. The first bullet forces target identification, stopping wrong directory scans. The fourth enforces approval-gated fix proposals, not unattended fixes, because the agent proposes a minimal diff.

## 7. Why pair Zed with LyraShield

Zed gives you speed and agent control, LyraShield adds verification and reporting that is designed to scale with AI built code. Pillar coverage from the [vibe coding security guide](/blog/vibe-coding-security-guide) explains why unverified scaffolding creates systemic risk across auth, injection and supply chain. Zed runs the tools, LyraShield provides the evidence trail from Target to Scan to Evidence State to Fix Proposal to Retest to Report. v1 is scoped to agentic pentest plus SCA plus secrets plus GitHub Action plus SARIF, so you can cover both code and dependencies without adding three separate scanners. Use the [Zed integration guide](/docs/integrations/zed) as the canonical config source and keep the loop explicit in pull request templates so reviewers see scan IDs and retest links.

To put this into practice, run your first scan in Zed, triage one finding with an evidence state, propose a Fix Proposal with tests and confirm the SARIF report in GitHub code scanning. Then expand your checklist with the [AI app security checklist](/tools/ai-app-security-checklist) and [create an account at LyraShield AI](https://app.lyrashieldai.com/sign-up) to track when Fix Proposal generation and full engine execution moves from designed to live. The pairing works because Zed minimizes friction between writing and checking, while LyraShield adds verification that generation skips.
