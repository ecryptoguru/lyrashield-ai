Fastest path: run `npx lyrashield init`, which detects Zed and writes the MCP config. Verify with `npx lyrashield doctor`, then `npx lyrashield login` to store credentials in ~/.lyrashield/credentials.json. The manual config below is what the CLI writes, kept for reference.

You can secure AI built apps in Zed by connecting LyraShield AI through the [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) and reviewing findings with recorded evidence states directly from the editor, then enforcing the same policy in CI with a diff aware GitHub Action gate. Zed reads servers from `settings.json` under `context_servers`, supporting local stdio and remote HTTP with a bearer key.

Zed is fast and agent native, which makes it popular for vibe coding, but speed can leave security gaps when dependencies and routes are scaffolded by agents. The [vibe coding security guide](/blog/vibe-coding-security-guide) frames this problem as unverified generation at scale. LyraShield AI is an agent native AppSec layer for AI built software that follows a loop of Target to Scan to Evidence State to Fix Proposal to Retest to Report. This post shows the exact Zed configuration for both local and remote MCP, how to verify the connection, how to run an inline check, and how to wire CI so findings stay actionable.

## 1. Prerequisites and setup

You need Zed 0.170 or newer, Node 18 or newer for `npx`, a LyraShield API key prefixed `lsk_` for remote mode, and a GitHub repo where you can add workflows. Restart Zed after you save the MCP configuration, then confirm the server in the Agent Panel. For remote mode, store your key as an environment variable and never commit it. Zed reads MCP servers from `settings.json` under `context_servers`, and the [Zed documentation](https://zed.dev/docs/assistant/context-servers) describes this field as the point where you add custom tools. Confirm you can read secrets scans and dependency data locally by checking your project against [OWASP Top 10](https://owasp.org/www-project-top-ten/) patterns and by reviewing vulnerable deps on [OSV](https://osv.dev/). If you have not used MCP before, skim the [MCP spec overview](https://modelcontextprotocol.io/specification/2025-03-26) to see how tools, resources, and prompts are exposed. Before editing `settings.json`, decide which transport suits your work, since both register under `context_servers` and you can switch without rewriting prompts.

## 2. Configure the MCP server in Zed

Zed supports local stdio and remote HTTP MCP servers. Use local for air gapped work and remote for shared team keys. Add one of these blocks to your Zed `settings.json`. The full reference lives in the [Zed integration guide](/docs/integrations/zed). Do not add bare paths elsewhere in your docs, always use markdown links like the [Zed integration guide](/docs/integrations/zed) to keep references valid.

Local stdio mode:

```json
{
  "context_servers": {
    "lyrashield": {
      "source": "custom",
      "command": {
        "path": "npx",
        "args": ["-y", "@lyrashield/mcp"],
        "env": {
          "LYRASHIELD_API_KEY": "${LYRASHIELD_API_KEY}"
        }
      }
    }
  }
}
```

Remote HTTP mode with Bearer:

```json
{
  "context_servers": {
    "lyrashield-remote": {
      "source": "custom",
      "command": {
        "path": "npx",
        "args": ["-y", "@lyrashield/mcp", "--remote"],
        "env": {
          "LYRASHIELD_API_KEY": "${LYRASHIELD_API_KEY}",
          "LYRASHIELD_API_URL": "https://app.lyrashieldai.com/api/mcp"
        }
      }
    }
  }
}
```

The remote URL is [https://app.lyrashieldai.com/api/mcp](https://app.lyrashieldai.com/api/mcp) and authenticates with `Authorization: Bearer lsk_...`. The stdio entry uses the pinned command `npx -y @lyrashield/mcp` as requested. You can also run the remote endpoint directly from tools that support streamable HTTP. Keep `$VAR` expansion explicit as shown, since Zed expands variables at launch. For comparison of editor setups, see the [Zed AI app security checklist](/blog/zed-ai-app-security-checklist) which walks through the same pattern for checklist driven reviews. The core difference is the `--remote` flag and `LYRASHIELD_API_URL` entry. In stdio mode the binary lives in the `npx` cache, pin a version if reproducibility matters. In remote mode the server is managed, but at the cost of network dependency, so editor and CI share the same finding IDs.

## 3. Verify the connection in Zed

Restart Zed after editing `settings.json`, then open the Agent Panel and run `/context_servers` to list active servers. You should see `lyrashield` or `lyrashield-remote` with a green status. Call `lyrashield_list_targets`, start an authorized scan, and poll it with `lyrashield_get_scan_status`. If you see a permission error, confirm that `LYRASHIELD_API_KEY` is set in the shell that launched Zed because context servers inherit environment variables at startup. A 401 from the remote endpoint means the key must be rotated and exported again.

## 4. Run an inline security check from the editor

With the server green, target your current project root and run a scan from the prompt. Ask Zed to summarize each finding with its recorded evidence state. Cross-check dependencies against [OSV](https://osv.dev/) and code patterns against [CWE Top 25](https://cwe.mitre.org/top25/archive/2024/2024_cwe_top25.html). `lyrashield_generate_fix_plan` is read-only, while `lyrashield_record_fix_proposal` records an approved remediation summary; neither edits code, creates a branch, or opens a PR. Apply the change in your normal development workflow, queue `lyrashield_verify_fix`, and poll the returned scan to a terminal state. Keep the loop as Target to Scan to Evidence State to Fix Proposal to Retest to Assurance Report. Call a result independently verified only when a separate verification receipt exists.

## 5. Wire the GitHub Action diff aware gate

Editor checks catch issues early, CI gates prevent drift on pull requests. Add `.github/workflows/lyrashield.yml` with a SARIF upload so results appear in GitHub code scanning. The [GitHub docs for SARIF upload](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github) describe the required `security-events: write` permission. The workflow below uses the same pinned `npx` and remote endpoint pattern and keeps secretsGitHub scanning broad.

```yaml
name: lyrashield diff gate
on:
  pull_request:
    branches: [main]
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - uses: ecryptoguru/lyrashield-ai@v1
        with:
          fail_on_severity: HIGH
```

This runs only on changed files, which keeps the gate fast and focused. SARIF output integrates with GitHub code scanning. If you need SCA and secrets history, see [docs.github.com on dependency review](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-supply-chain-security) for supply chain context. The action derives the pull-request diff, so a one-line edit avoids a full scan. SARIF lands in the GitHub Security tab, where each rule maps to a file and line. The local MCP server and the runner-local CI gate are complementary checks, not the same remote scan.

## 6. Add agent rules snippet

Add a short rule file so every agent session in Zed follows the same security loop. Save as `.agent/rules/security.md` or the equivalent rules directory you use.

```md
# Security rules for Zed agents

- Always start with Target identification: root, env, and data class.
- Run LyraShield scan via MCP before proposing large refactors.
- Treat only findings with evidence states as blocking. Include evidence in the PR description.
- For Fix Proposal, propose minimal diff, add tests for the finding with an evidence state, and request retest.
- Update Report notes with scan ID and SARIF link.
```

This keeps behavior consistent between human and agent edits. The rule avoids phrases implying unattended fixes and frames the Fix Proposal as a proposed change designed to be reviewed. Think of the rules file as the contract your agent follows unsupervised. The first bullet forces target identification, stopping wrong directory scans. The fourth enforces approval-gated fix proposals, not unattended fixes, because the agent proposes a minimal diff.

## 7. Why pair Zed with LyraShield

Zed gives you speed and agent control, LyraShield adds verification and reporting that is designed to scale with AI built code. Pillar coverage from the [vibe coding security guide](/blog/vibe-coding-security-guide) explains why unverified scaffolding creates systemic risk across auth, injection, and supply chain. Zed runs the tools, LyraShield provides the evidence trail from Target to Scan to Evidence State to Fix Proposal to Retest to Report. v1 is scoped to agentic pentest plus SCA plus secrets plus GitHub Action plus SARIF, so you can cover both code and dependencies without adding three separate scanners. Use the [Zed integration guide](/docs/integrations/zed) as the canonical config source, and keep the loop explicit in pull request templates so reviewers see scan IDs and retest links.

To put this into practice, run your first scan in Zed, triage one finding with an evidence state, propose a Fix Proposal with tests, and confirm the SARIF report in GitHub code scanning. Then expand your checklist with the [AI app security checklist](/tools/ai-app-security-checklist) and [create an account at LyraShield AI](https://lyrashieldai.com) to track when Fix Proposal generation and full engine execution moves from designed to live. The pairing works because Zed minimizes friction between writing and checking, while LyraShield adds verification that generation skips.
