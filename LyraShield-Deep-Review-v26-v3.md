## P1 findings

### P1-1 — Scanner CPU exhaustion: confirmed locally

**Evidence:** `apps/worker/src/engine/scanners/php-runtime.ts:132` contains:

```ts
const directive = /^\s*#\s*(syntax|check|escape)[ \t]*=[ \t]*(.*?)\s*$/i.exec(line)
```

For `#syntax=a` followed by N spaces and `x`, the trailing whitespace matcher repeatedly retries over overlapping suffixes. The IaC scanner permits files up to 512 KiB and calls PHP runtime discovery before deciding whether a Dockerfile describes PHP. `scanner-orchestrator.ts` invokes these deterministic scanners in the Node worker process. A timer-based `withScannerPhaseTimeout` cannot interrupt synchronous JavaScript while that event loop is blocked.

Fresh bounded measurements, in milliseconds (single samples, diagnostic rather than benchmark guarantees):

| Source expression                                                         | 10,000 characters | 20,000 | 40,000 |
| ------------------------------------------------------------------------- | ----------------: | -----: | -----: |
| Docker parser directive                                                   |              68.3 |  256.9 |  950.4 |
| Gradle assignment (`dependency-manifests.ts:353`), spaces followed by `!` |              60.5 |  240.8 |  962.7 |
| OpenAPI `/\{[^}]+\}/`, unmatched `{` characters                           |              45.8 |  181.8 |  728.2 |

The growth supports super-linear CPU cost. The original six-minute extrapolation was not executed and is removed as a measured claim. Gradle's manifest fallback has a 512 KiB cap. OpenAPI **does** have a response cap: `openapi-scanner.ts` passes `profile.maxResponseBytes`; current profiles in `packages/types/src/url-scan-capabilities.ts` use 2–5 MiB. A document cap is not a path-string complexity bound.

The PHP source lead is also supported: nested `system(` calls around `$_GET["x"]` took approximately 15/52/225 ms for 100/200/400 calls (305/605/1,205 tokens). `inspectStatement` repeatedly finds closing tokens, slices arguments and analyzes overlapping expressions. It still returns one deduplicated finding. The 2,048-token statement cap and 100-finding cap do not prevent expensive work within one statement. The original 19-statement/27-second result was not reproduced.

**Impact:** attacker-controlled input can delay other scans, heartbeat and job-lock work in the same worker process. This is not proof that every worker or the whole fleet stops. Repository and OpenAPI entry paths have their normal authorization/admission prerequisites. This validation did not execute a hosted exploit.

**Corrections to the fix:**

- Bound parser work before expensive expressions. Parse directives and assignments without overlapping whitespace quantifiers. Trimming alone does not make every possible replacement regex linear.
- Oversized or unsupported input must produce explicit incomplete coverage; never silently truncate it into a clean scan. Preserve the original file identity/checksum.
- An 8 KiB line limit is a proposed policy, not an already justified universal limit. Handle minified files, multiline constructs and valid large manifests deliberately.
- Add a per-statement work/depth budget and avoid rescanning nested token ranges. Deduplicate findings for reporting while retaining a separate operation budget. Simply counting findings only after deduplication could allow more work.
- Yield between bounded chunks and check elapsed time. Yielding between files cannot rescue a single blocking regex; an isolated worker thread/process offers an enforceable timeout if required.
- Use deterministic operation/input limits plus isolated hard-timeout regression tests. Warmed repeated n/2n samples are supplementary; a ratio under 3 is neither flake-free nor proof of linear complexity.
- The vulnerable TypeScript runs in the **shared worker process**, not inside the engine scan sandbox. Moving it across a process boundary needs isolation review, but a parser repair is not itself a sandbox-capability change. A file-wide lint suppression exists; whether the lint rule detects this exact expression was not established.

### P1-2 — Settlement refusal can roll back consumed usage: confirmed code path; database exploit unexecuted

**Evidence:** `apps/worker/src/jobs/run-scan/settlement.ts:72-159`, `packages/billing/src/usage/meter.ts:222-405`, `packages/billing/src/grace.ts:91-189`, `apps/worker/src/jobs/run-scan/finalization.ts:593-620`.

`recordAgentMinutes` writes usage and pack debits inside an account-bound Serializable transaction. Its `settleOverage` callback runs before commit. Without eligible paid overage, that callback passes the **entire engine wall-clock duration** to `enterGrace`. If grace reaches its cap, it sets `STOPPED_BUDGET` and throws while the transaction is active. Usage, pack debits and the grace update roll back. The caller audits the refusal and subsequently finalizes evidence. A separate settlement-intent scan event can survive; “only an audit row survives” was inaccurate.

The normal admission path permits a positive remaining balance. The runtime ceiling is based on mode, policy and execution plan, not the remaining account balance. Thus a completed, billable run that exhausts grace can preserve its balance and leave no `agent_minutes` receipt. A subsequent attempt can pass that balance test, subject to other admission/rate/concurrency controls. Refused Launch Assurance overage also throws within the same transaction.

**Qualification:** a “5-minute pool, 45-minute scan” illustrates the transaction path only if the selected profile/policy permits that runtime and the run reaches billable settlement. It is not a demonstrated production exploit. Remove the unverified `$0.05/min` COGS estimate and `$2 per repeat` claim. Existing mocked tests cover refusal, but do not prove the full repeat cycle on PostgreSQL.

**D1 needs more than a timer:**

1. Budget in **billable agent-minutes**, including `ceil(wallClockMs / 60_000)` and the Deep/Custom 3× multiplier. Convert the permitted billable amount to a wall-clock limit without rounding upward beyond capacity.
2. Resolve pool, packs, unused grace and eligible **remaining** overage headroom for the sponsor account. A spend-limit setting is cents, not minutes; subtract already-consumed overage and respect plan eligibility.
3. Reserve or otherwise serialize concurrent capacity across all workspaces sponsored by that account. A start-time snapshot alone can be spent twice.
4. Stop latency is a safety margin to reserve within the authorized envelope, or explicitly record as absorbed cost. An arbitrary extra two billable minutes is not free capacity and does not guarantee that settlement succeeds.
5. Fix the settlement disposition as well as runtime admission. `finalization.ts` currently passes outcome `failed` when `budgetExceeded` or a pre-existing `STOPPED_BUDGET` is present; `createEngineMinuteMeter` skips billing for `failed`. Adding a smaller runtime ceiling without distinguishing this path may still produce an unbilled result. Preserve the standing failed-scan policy; explicitly design the billable partial/budget outcome.
6. Persist an idempotent receipt/disposition for admitted billable work without rolling back all covered usage merely because the remaining allowance is exhausted. Exact-cap exhaustion must stop future admission without invalidating already-covered work. Do not introduce an ad hoc second charging transaction that loses finalization atomicity or double-charges a retry.

**Required tests before closure:** PostgreSQL reproduction of first refusal and repeat admission; grace below/at/above cap; partially used grace; pool-plus-pack spillover; Deep rounding; remaining spend limit; two concurrent scans across workspaces; cancellation; failed/pre-provider non-billing; evidence-finalization failure; process interruption and idempotent retry. No paid production over-budget test is authorized by this document.

### P1-3 — Target-scoped OAuth reads escape target restrictions (original P2-12)

**Confirmed in source.** `GET /api/findings`, `GET /api/fix-proposals` and `GET /api/launch-readiness` enforce workspace permission but do not apply `assertOAuthDelegatedScope` or filter by the connection's `allowedTargetIds`. Findings statistics are a branch of the findings route, not a separate `/api/findings/stats` route. `/api/v1/launch-readiness` shares the handler.

`packages/auth/src/session.ts:43-57` shows that delegated target restrictions are a separate check. A scoped credential belonging to an authorized member can request another target or omit the target and receive workspace-wide results. Readiness can include target names, conditions and finding counts. Workspace RLS does not enforce a credential's narrower target grant.

This is a credential authorization boundary within a workspace, not demonstrated cross-workspace access. Under recorded D4, it is a security correction rather than an optional product decision; prioritize it with the P1 fixes. Actual production exposure was not queried and is not a prerequisite for correcting the check.

**Fix:** one shared read-scope resolver; explicit targets must be authorized. List data, statistics, counts and pagination must all use the same allowed-target predicate. Empty allowed-target lists return no target data. A target-scoped readiness request without `targetId` returns 403 as D4 records. Test in-scope, out-of-scope, missing-target, all-target, empty-grant and revoked/expired credentials. Preserve browser-session and API-key contracts. Do not expose a subset result as a workspace-wide readiness verdict.

#### P2-16 details and tests

- **PHP attributes:** the lexer consumes `#[` as a comment. A fresh probe using a multiline `#[ Example ]` attribute before `function f() {}`, followed by `$x=$_GET["x"]; system($x);`, loses the CWE-78 finding that the same file without the attribute produces. It also reports unbalanced syntax. A direct sink can still be found, so “all later sinks are missed” would be too broad. Add attribute-aware tokenization and local-flow fixtures.
- **PHP close tags in line comments:** `//` and `#` consume through newline without respecting `?>`, leaving the parser in the wrong mode. The [PHP comment specification](https://www.php.net/manual/en/language.basic-syntax.comments.php) ends these comments at either newline or the end of the PHP block. Test mixed HTML/PHP boundaries and prevent both false positives and false negatives; the simple probes here establish wrong tokens, not universal missed sinks.
- **Finding IDs include line numbers:** confirmed in `buildFinding` and runtime findings. That alone does not establish broken persistence/retest identity; trace downstream deduplication and receipts before changing IDs or migrating history.
- **EOL:** the `<8.2` threshold is hard-coded, while the pinned catalog dated 2026-10-23 lists 8.2–8.5 as supported. This is a future catalog-drift risk, not evidence that 8.2 is currently misclassified. Move lifecycle data into a reviewed dated catalog.
- **Runtime advisories:** unknown extensions allow candidate advisories, but output explicitly says runtime installation, exploitability and configuration are unverified. Retaining upstream severity is not equivalent to claiming confirmed exploitability. The exact “28 advisories” count depends on the precise patch and was not reproduced. Improve applicability labels/filtering from known facts; never suppress unknown applicability as safe.
- **IaC context:** line rules can flag a previously declared Docker stage alias, unresolved `${BASE_IMAGE}`, an earlier `USER root` followed by a non-root final user, and `*_FILE` secret paths. The Compose regex misses the usual spaced list form `- PASSWORD=value`. Terraform CIDR matching needs ingress/egress context. Add minimal positive and negative fixtures and parse stage/resource context before changing heuristics.
- **Benchmark:** the fixture suite checks CWE sets and the generic `unassessed` limitation. The latter is always present by construction; it tests disclosure, not detection accuracy. The CWE checks remain meaningful. Add per-sink count, source location and precision/recall assertions for the affected fixtures rather than dismissing the whole suite.
